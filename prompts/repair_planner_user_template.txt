Подготовь короткий план repair для уже сгенерированной правки Python-кода.

Верни только валидный JSON.

Обязательные поля JSON:
- status
- repair_objective
- allowed_calls_to_use
- forbidden_calls
- required_changes
- reason

Правила:
- JSON должен содержать только следующие ключи верхнего уровня: "status", "repair_objective", "allowed_calls_to_use", "forbidden_calls", "required_changes", "reason". Все эти ключи обязательны. Не добавляй другие ключи, не переименовывай ключи, не переводи имена ключей, не добавляй пробелы в начале или конце имени ключа, не используй похожие или сокращенные варианты. Имя каждого ключа должно совпадать с указанным списком посимвольно.
- status используй только "repairable" или "not_repairable".
- Если исправление требует вызова метода зависимости, которого нет в Allowed API Surface или known_methods_by_type, верни status="not_repairable".
- Блок Allowed API Surface ограничивает вызовы методов и атрибутов проектных зависимостей, сервисов, вспомогательных объектов проекта и внутренних проектных контрактов. Он не запрещает использовать стандартную библиотеку Python и обычные методы явно видимых стандартных типов, если это нужно для задачи, не добавляет внешних зависимостей и не противоречит видимому коду.
- Если ошибка возникла из-за выдуманного метода проектной зависимости, не заменяй его другим выдуманным методом. Сначала проверь, можно ли выполнить задачу обычными средствами стандартной библиотеки или методами явно видимого стандартного типа, либо через уже видимый проектный контракт.
- Не считай отсутствие метода стандартного типа в Allowed API Surface причиной отказаться от реализации. Это ограничение применяется к проектным зависимостям и внутренним проектным контрактам, а не к стандартной библиотеке Python.
- Если исходная генерация пыталась использовать недоступный широкий сценарий, но есть безопасный более узкий видимый контракт, repair считается repairable: замени широкий сценарий на этот видимый контракт и при необходимости добавь обязательный параметр в новый symbol.
- Если нужно убрать недоступный широкий сценарий, не заменяй его другим широким методом по догадке; используй видимый параметризованный контракт и добавь его обязательные параметры в новый symbol. Если проблема связана с восстановлением модели из сериализованных данных, планируй явное преобразование значений к видимым типам полей и не планируй передачу None в поле с видимым значением по умолчанию.
- Нельзя считать repair not_repairable только потому, что нет метода для получения всех сущностей; если видим contract с обязательным параметром, используй этот параметризованный путь.
- not_repairable возвращай только если невозможно исправить без нового production contract, нового dependency method, нового import path или несуществующего поля результата.
- Если можно исправить без выдумывания новых контрактов, верни status="repairable".
- Если ошибка проверки указывает, что в конструктор проектной модели передано сериализованное значение вместо видимого типа поля, repair считается repairable, если значение можно явно преобразовать к видимому типу с помощью стандартного или видимого проектного способа.
- Не придумывай новые методы зависимостей, новые поля объектов, новые import path или новые сервисные контракты.
- Если diagnostics предлагает использовать имя уровня модуля без `self`, используй это имя напрямую и не добавляй к нему `self.`.
- Если ошибка содержит `unknown_self_attribute`, `unknown_self_method` или `unknown_injected_dependency_attribute`, план repair должен требовать полного удаления неизвестного self-атрибута или self-метода и использования только видимых атрибутов/методов из диагностики.
- Если ошибка проверки показывает, что предыдущий код использовал несуществующий способ найти или получить данные, сначала проверь видимые методы того же класса из контекста. Если есть метод, который покрывает нужную часть поведения и подходит по сигнатуре, планируй его использование вместо выдуманного метода или неверного вызова зависимости.
- Если ошибка содержит `unknown_runtime_name`, план repair должен либо добавить недостающий import, либо заменить имя на уже видимое имя из контекста.
- allowed_calls_to_use перечисляй только из Allowed API Surface, production contracts или явно видимого контекста.
- forbidden_calls перечисляй из error context и из любых неразрешенных вызовов.
- required_changes должны быть конкретными и короткими.
- Все текстовые значения пиши на русском языке.
