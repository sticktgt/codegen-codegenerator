Проанализируй результат генерации Python-кода. Основной код прошел базовые проверки, но сгенерированный тест не прошел verification.

Верни только валидный JSON без markdown.

Обязательные ключи JSON:
- verdict
- confidence
- production_code_quality
- generated_test_quality
- should_keep_production_code
- recommended_action
- reasons
- production_risks
- test_issues
- recommendation_summary
- next_steps

Допустимые значения verdict:
- production_likely_ok_test_likely_bad
- production_likely_bad_test_valid
- both_uncertain
- environment_or_import_issue
- insufficient_context

Допустимые значения should_keep_production_code:
- yes
- no
- manual_review

Допустимые значения recommended_action:
- keep_production_code_exclude_test
- reject_production_code
- manual_review
- rerun_test_generation

Общие правила:
- Не принимай окончательное решение за пользователя. Дай рекомендацию для ручной проверки.
- Оцени, соответствует ли основной код исходному запросу и видимому проектному контексту.
- Оцени, относится ли ошибка к тесту, окружению запуска или основному коду.
- Если контекста недостаточно для уверенного вывода, используй verdict="both_uncertain" или verdict="insufficient_context".
- Ответ должен быть кратким, но понятным человеку, который решает: сохранять основной код или отклонить его.
- В `recommendation_summary` дай одну ясную рекомендацию для ручного решения: что делать с production-кодом и что делать с generated test.
- В `next_steps` дай 1-4 конкретных следующих действия. Не ограничивайся общим `manual_review`, если из контекста видно, что production можно оставить, тест исключить или тест нужно перегенерировать.
- В `reasons`, `production_risks` и `test_issues` указывай, на чем основан вывод: diff, старый target-код, полный исходный файл, verification context или сгенерированный тест. Если нужный контекст отсутствует или обрезан, явно напиши, что уверенность ограничена.

Правила оценки основного кода:
- Если ошибка возникает при импорте, сборе тестов или выполнении теста из-за исключения внутри измененного основного модуля, считай это риском основного кода.
- Если traceback указывает на отсутствующее имя, импорт, метод, поле, аннотацию, зависимость или ошибку исполнения внутри основного кода, считай это риском основного кода, если нет явного доказательства, что тест неверен.
- Если основной код нарушает исходный запрос, видимый проектный контракт или уже существующее публичное поведение, не скрывай это за плохим тестом.
- Если основной код добавляет import path, который не подтвержден видимым проектным контекстом, или вызывает project symbol через модуль, где этот symbol не виден, считай это production_risk даже при ошибках generated test.
- Если основной код создает project model/result-object с keyword-аргументами, которых нет в видимой сигнатуре, model surfaces, source excerpt или явных требованиях запроса, считай это production_risk.
- Для replace_symbol класса считай существующие публичные методы частью сохраняемого публичного поведения, если пользователь явно не просил менять или удалять их.
- Если сгенерированный тест проверяет поведение существующего публичного метода, которое было явно описано в старом docstring, старом коде или verification context, не считай такой тест плохим только потому, что это поведение не было повторено в новом запросе.
- Если verification context содержит предупреждение possible_existing_method_contract_lost, считай это риском основного кода, пока не увидишь явное указание пользователя изменить или удалить это поведение.
- Если verification context содержит предупреждение или ошибку о перестановке присваивания и последующего использования значения в сохраняемых данных, return или вызове, считай это риском основного кода. Не рекомендуй сохранять production-код только потому, что generated test тоже плохой.
- Если diff основного кода показывает удаление ключа из явно создаваемого словаря, JSON-структуры или сохраняемых данных, а пользовательский запрос требует сохранить формат/структуру данных, считай это production_risk даже при плохом generated test.
- Старый target-код и полный исходный файл до изменения используй как справочный источник старого публичного поведения, формата данных, импортов и surrounding context. Сгенерированный target-код остается источником того, что реально предлагается к merge; если он потерял поведение из старого target-кода без явного требования пользователя, укажи production_risk.

Правила оценки теста:
- Если тест использует несуществующие поля, методы, импорты, неверные аргументы конструктора или API, укажи это в test_issues.
- Если verification context говорит, что test присваивает project model field после создания, но это поле видно как constructor field/model surface, считай это проблемой способа подготовки тестовых данных: тест должен передать значение через конструктор, а не утверждать, что поле не существует.
- Если generated test падает из-за вызова видимого project class/function/method без обязательных аргументов, указанных в видимой сигнатуре, считай это проблемой generated test, а не environment/import issue, если нет признаков ошибки production-кода.
- Если тест проверяет поведение, которое не описано в запросе, старом публичном поведении, старом docstring, старом коде или видимом контексте, это может быть проблемой теста.
- Если тест падает из-за проблемы в основном коде, не называй качество теста bad только из-за факта падения.

Правила согласованности ответа:
- Если production_risks содержит существенный риск основного кода, should_keep_production_code не может быть "yes". Используй "manual_review" или "no".
- Если production_risks содержит существенный риск основного кода, recommended_action не должен быть "keep_production_code_exclude_test". Используй "manual_review" или "reject_production_code".
- Если причины или production_risks указывают, что основной код мог нарушить существующее поведение или требования запроса, verdict не должен быть "production_likely_ok_test_likely_bad". Используй "production_likely_bad_test_valid" или "both_uncertain".
- Если test_issues говорят, что тест корректен или в целом уместен, но основной код не запускается или нарушает поведение, generated_test_quality не должен быть "bad".
- Поля verdict, should_keep_production_code и recommended_action должны быть логически согласованы с reasons, production_risks и test_issues.
- Если production checks прошли, старый target/full-file context доступен, diff не показывает production-регрессий, а явная ошибка связана только с неверным generated test usage проекта, предпочитай verdict="production_likely_ok_test_likely_bad" и recommended_action="keep_production_code_exclude_test". В recommendation_summary явно напиши, что production можно оставить для ручного merge review, а тест исключить или перегенерировать.
- Если сомневаешься, выбирай более осторожный вариант: verdict="both_uncertain", should_keep_production_code="manual_review", recommended_action="manual_review".
