Правила:
- Не принимай окончательное решение за пользователя. Дай краткую рекомендацию для ручного review.
- Сначала проверь, нарушает ли production-код исходный запрос, видимый контракт или существующее публичное поведение.
- Затем проверь, является ли падение следствием плохого generated test setup, неверного import/API, слишком точных assert-ов или проблемы окружения.
- `planner_result` используй по ролям: explicit_requirements/preserve_literals — требования к наблюдаемому поведению, implementation_constraints — технический контекст, suggested_reuse — необязательные варианты реализации, forbidden_assumptions — запреты на неподтвержденные допущения. Если planner_result добавляет детали из старого кода/docstring/реализации, не считай их обязательными требованиями без подтверждения в исходном запросе.
- Если verification context содержит static/relevance issues generated test, используй их как важные факты о качестве теста.
- Если static issues говорят, что generated test использует `__new__`, обходит конструктор или создает реальный parent instance без необходимости, считай это проблемой generated test setup. В next_steps рекомендуй облегчить setup и следовать target-derived strategy: не создавать тяжелый объект, если target-код не требует состояния реального экземпляра.
- Если traceback указывает на ошибку внутри production-кода, отсутствующий import/name/method/field или нарушение явного требования пользователя, добавь production_risk.
- Если ошибка вызвана тем, что тест создает лишний project object, неверно вызывает constructor, использует несуществующий API, вручную повторяет generated string/path/id или делает слишком конкретный assert, добавь test_issue.
- Если production_risks содержит существенный риск, не возвращай `production_likely_ok_test_likely_bad`, `production_code_quality="good"`, `should_keep_production_code="yes"` или `keep_production_code_exclude_test`.
- Если production_risks содержит runtime/API/import/name/attribute/method/contract error, верни `production_likely_bad_test_valid` или `both_uncertain`, выставь `production_code_quality` как `bad` или `uncertain`, а `should_keep_production_code` как `no` или `manual_review`. Не называй generated test главной проблемой, если traceback или static diagnostics указывают на ошибку production-кода.
- Если generated test проверяет наблюдаемое требование, прямо указанное в исходном пользовательском запросе или explicit_requirements, не считай такой assert ошибкой теста без явного доказательства, что production-код реализует это требование другим корректным способом. Если тест проверяет только suggested_reuse, считай это проблемой теста, если symbol не является обязательным и не входит в наблюдаемый результат.
- Если production checks прошли и основная проблема в generated test, оцени, можно ли автоматически исправить generated test без изменения production-кода. Заполни generated_test_repairability, generated_test_repair_kind, generated_test_repair_instructions и generated_test_repair_risks.
- Используй generated_test_repairability="repairable", если ошибка теста локальная и исправляется изменением setup, patch target, constructor args, слишком точных assert-ов или ручного oracle без новой информации о production-коде.
- Если production checks прошли, а generated test падает из-за создания настоящего parent/application/window/controller/service объекта, тяжелого конструктора, framework runtime, event loop, UI/runtime инициализации или похожего setup, считай тест repairable или maybe_repairable, если проверяемый target method можно вызвать через fake/minimal self, stub, monkeypatch или локальный fake dependency без изменения production-кода. Для такого случая обычно используй generated_test_repair_kind="bad_setup_heavy_parent_instance".
- Не используй generated_test_repairability="not_repairable" только потому, что текущий тест зависит от framework/runtime окружения. Если эту зависимость можно убрать заменой setup теста на fake/stub/monkeypatch, выбери "repairable" или "maybe_repairable".
- Используй generated_test_repair_kind="environment_only" только если проблема действительно сводится к отсутствующему внешнему окружению, пакету или pytest plugin и не исправляется переписыванием самого generated test setup. Если тест сам создает лишний тяжелый объект или использует optional plugin fixture без необходимости, это проблема теста, а не чистая environment-only проблема.
- Используй generated_test_repairability="maybe_repairable", если repair возможен, но не хватает части контекста или есть риск неоднозначности setup.
- Используй generated_test_repairability="not_repairable", если ошибка теста неотделима от production-risk, зависит от окружения так, что ее нельзя убрать переписыванием теста, требует нового project contract или требует ручного решения пользователя.
- Используй generated_test_repairability="not_needed", если generated test не требует исправления или review не про ошибку generated test.
- Не ограничивай review только первой ошибкой verification. Всегда дополнительно посмотри сам generated test: создает ли он настоящий parent/application/window/controller/service object, использует ли optional pytest plugin fixture, тяжелый constructor или runtime setup, хотя target-код можно проверить через fake/stub.
- Если generated_test_repair_kind="bad_setup_heavy_parent_instance", то generated_test_repair_instructions ОБЯЗАТЕЛЬНО должны содержать указание убрать настоящий parent constructor, подготовить minimal fake/self object, перечислить нужные fake/self поля и сохранить только проверки наблюдаемого поведения. Не ставь этот repair_kind, если инструкции фактически предлагают только import или minor syntax fix.
- Если static diagnostics сообщает `generated_test_calls_project_instance_method_on_class`, проверь, был ли это exact target method. Для exact target method допустима рекомендация `ParentClass.target_method(fake_self, ...)` с минимальными fake dependencies. Для любых других project instance methods не рекомендуй class-level вызов и не рекомендуй реальный heavy parent instance.
- Если есть одновременно простая статическая ошибка теста и тяжелый parent/runtime setup, укажи обе проблемы в test_issues и включи обе правки в generated_test_repair_instructions.
- В generated_test_repair_instructions пиши конкретные инструкции для будущего repair generated test: что убрать, что замокать, какие поля fake/self подготовить, какие assert-ы заменить и какие production checks сохранить. Не предлагай менять production-код в этом поле.
- Если production checks прошли, явных production_risks нет, а ошибка связана только с generated test, используй `production_likely_ok_test_likely_bad` и рекомендуй исключить или перегенерировать тест.
- Если не можешь уверенно отделить ошибку теста от ошибки production-кода, используй `both_uncertain`, `manual_review`.
- Поля verdict, quality, action, reasons, production_risks и test_issues должны быть согласованы.
- Пиши кратко и понятно для человека.
