Подготовь компактный план изменения Python-кода.

Верни только валидный JSON.

Обязательные поля JSON:
- operation
- target_file
- target_symbol
- intent_summary
- constraints
- reference_symbol
- insert_scope
- expected_new_symbol_kind
- parent_qualname
- explicit_requirements
- implementation_constraints
- suggested_reuse
- forbidden_assumptions
- preserve_literals

JSON должен содержать только перечисленные поля верхнего уровня. Не добавляй поля `code`, `import_changes`, `test_file`, `source_code`, `target_qualname`, `insert_after` или другие поля code artifact.

Приоритет исходного пользовательского запроса.
Выполни требования из блока ниже. Справочный код, документация, комментарии, примеры, related symbols, related tests, reference artifacts, reuse hints и planner wording нужны для понимания проекта, сигнатур, импортов, стиля и допустимых API.
Если справочный контекст противоречит исходному пользовательскому запросу, приоритет имеет исходный пользовательский запрос.

Исходный пользовательский запрос:
{request}

Правила:
- Если исходный запрос шире видимого project API, выбери самый узкий безопасный видимый контракт и добавь необходимые параметры в новый symbol, либо верни status="not_enough_context".
- Планируй вызовы project dependencies и внутренних project contracts только по явно видимым access path, method names и сигнатурам. Ограничения project API не запрещают стандартную библиотеку Python и обычные операции явно видимых стандартных типов.
- Если у текущего класса или параметра явно виден стандартный тип Python, планируй использование его обычных операций и методов вместо выдумывания нового проектного helper-метода.
- Если в контексте есть Required production contract calls, планируй обязательный вызов этих production-контрактов в новом code; не заменяй их ручной реализацией бизнес-логики.
- Если видимый production contract принимает обязательный параметр, планируй этот параметр в сигнатуре нового symbol или бери его из явно видимого local context; не планируй placeholder literal.
- Если строишь return_shape или explicit dict из результата production-контракта, используй только поля, явно видимые в contract/source context. Если нужных полей не видно, верни status="not_enough_context" или status="needs_planning".
- Не придумывай файлы и symbols.
- Используй только предоставленные target-данные.
- Поле intent_summary должно быть коротким и конкретным.
- Поле constraints должно быть JSON-массивом коротких общих ограничений.
- Поле implementation_constraints должно быть JSON-массивом технических ограничений применения: scope, target, allowed calls, import/API constraints, reuse constraints.
- Поле suggested_reuse должно быть JSON-массивом объектов вида {{"symbol": "...", "reason": "...", "required": false}}. Указывай здесь видимые related/helper/dependency symbols, которые могут быть полезны для реализации, но не являются требованием пользователя. Значение required=true допустимо только если пользователь прямо назвал этот symbol или явно потребовал именно этот вызов.
- Поле forbidden_assumptions должно быть JSON-массивом коротких запретов на неподтвержденные допущения, которые модель не должна превращать в поведение.
- Поле reference_symbol может быть null.
- Все текстовые значения в JSON пиши на русском языке.
- Не смешивай русский и английский язык в тексте ответа.
- Для замены существующего symbol используй только operation="replace_symbol".
- Если operation="replace_symbol" и target_symbol является существующим class, планируй замену самого класса: результат должен быть полным определением этого же класса, а не набором свободных top-level функций, helper-функций или отдельных методов.
- Если пользователь просит, чтобы существующая модель или класс «умели» выполнять действие, и target_symbol является class, планируй это поведение внутри класса как методы или поля класса, если пользователь явно не попросил вынести поведение в свободные функции.
- Для вставки нового symbol после anchor-symbol используй только operation="insert_after_symbol".
- Если requested operation=insert_after_symbol, поле target_symbol — это anchor-symbol, после которого должен быть добавлен новый symbol.
- Для insert_scope используй только "module_body" или "class_body".
- Если добавляется метод внутрь класса, используй insert_scope="class_body", expected_new_symbol_kind="method" и заполни parent_qualname.
- Если добавляется top-level функция или класс, используй insert_scope="module_body".
- В explicit_requirements сохрани только требования, которые прямо следуют из исходного пользовательского запроса: что нужно создать или изменить, явные имена symbols, сигнатуры, параметры, ожидаемые строки результата и явно заданное поведение.
- Не добавляй в explicit_requirements требования из старого docstring, target source, related symbols, reuse hints, Allowed API Surface, knowledge description или reference context, если пользователь не указал их явно. Если старое описание противоречит запросу пользователя, запрос пользователя имеет приоритет.
- Не пиши в explicit_requirements формулировки вида «использовать <symbol>», «вызвать <helper>», «переиспользовать <dependency>» или «импортировать <module>», если пользователь прямо не просил использовать именно этот symbol/API.
- В explicit_requirements не записывай технические вызовы вроде class/type-level contract names, если пользователь описал только наблюдаемое поведение. Точный receiver, import и сигнатура относятся к implementation_constraints/suggested_reuse.
- Разделяй требования пользователя и технический способ реализации: explicit_requirements описывает ожидаемое поведение результата; implementation_constraints описывает технические ограничения применения; suggested_reuse описывает необязательные видимые symbols/API, которые можно использовать, если они подходят по контракту.
- Если related symbol, helper, dependency method или production contract выглядит полезным для реализации, добавь его в suggested_reuse, а не в explicit_requirements. Если это обязательный видимый production contract из контекста, отрази это в implementation_constraints и suggested_reuse.required=true только при явном подтверждении в запросе или в Required production contract calls.
- Если справочный контекст предлагает неподтвержденный helper, специальный формат, локализацию, импорт, поле или внутренний алгоритм, добавь запрет в forbidden_assumptions и не превращай это в требование пользователя.
- В preserve_literals включай только значения, буквально написанные пользователем в Title, Description или Request constraints: имена symbols, сигнатуры, параметры, форматы строк, строки результата и другие литералы, которые нельзя переименовывать или переинтерпретировать.
- Если пользователь явно описывает наблюдаемый формат результата, return-shape, обязательный префикс/суффикс, расширение, ключевую строку или другой литерал, включи соответствующий literal/format marker в preserve_literals и не заменяй его старым docstring.
- Не добавляй в preserve_literals фрагменты старого кода, target source, related tests, planner wording или reference artifacts, если пользователь не написал эти значения явно.
- Если пользователь просит изменить текст, строку, формат или поведение, не сохраняй старое значение из текущего кода как preserve_literals.
