Сгенерируй изменение Python-кода для одной задачи.

Верни только валидный JSON требуемого формата.

Обязательные ключи верхнего уровня JSON:
- target_file
- target_symbol
- operation
- code
- import_changes
- target_qualname
- insert_scope
- expected_new_symbol_kind
- parent_qualname

`import_changes` всегда должен быть JSON-массивом. Если сгенерированный `code` использует имя из блока `Required import_changes for names used by generated code`, этот import должен быть включен в `import_changes`.

Правила:
- Если новый symbol объявлен как возвращающий dict, не возвращай напрямую объект/model/result из production-контракта с недиктовым типом; сформируй dict явно по видимым полям/атрибутам или используй явно видимый project helper.
- Если формируешь dict из результата production-контракта, используй только поля/атрибуты, явно видимые в Allowed API Surface, contract context или source excerpt. Не придумывай поля модели результата по смыслу запроса.
- Если новый code вызывает метод у внедренной зависимости или поля объекта, например `self.<dependency>.<method>(...)`, этот метод должен быть явно видим в target source, module/full file context, related symbols или contract context. Не придумывай новые методы зависимостей по смыслу запроса; если нужного метода нет в контексте, используй видимый контракт или измени сигнатуру нового symbol.
- Если Allowed API Surface передан в контексте, любые вызовы методов зависимостей должны совпадать с ним буквально по access path и имени метода.
- Блок Allowed API Surface ограничивает вызовы методов и атрибутов проектных зависимостей, сервисов, вспомогательных объектов проекта и внутренних проектных контрактов. Он не запрещает использовать стандартную библиотеку Python и обычные методы явно видимых стандартных типов, если это нужно для задачи, не добавляет внешних зависимостей и не противоречит видимому коду.
- Если у текущего класса, параметра или локального значения явно виден стандартный тип Python, используй обычные операции и методы этого типа вместо выдумывания нового проектного helper-метода или нового метода зависимости. Например, для обхода, чтения, проверки существования, преобразования или работы с коллекциями используй видимые возможности стандартных типов и стандартной библиотеки, если они подходят задаче.
- Ограничение на выдумывание методов относится прежде всего к проектным объектам и зависимостям. Не отказывайся от реализации только потому, что обычный метод стандартного типа не перечислен в Allowed API Surface.
- Если в контексте есть Required production contract calls, сгенерированный code обязан вызвать эти production-контракты; не реализуй их бизнес-логику вручную в API/adapter-слое.
- Если Allowed API Surface передан в контексте, любые вызовы методов зависимостей должны совпадать с ним буквально по access path и имени метода. Не заменяй отсутствующий метод похожим именем и не создавай новый способ доступа по смыслу запроса.
- Если для вызова production contract нужен обязательный аргумент, которого нет в текущем методе, добавь этот аргумент в сигнатуру нового symbol или используй явно видимую local variable; не подставляй placeholder literal или обобщающее значение.
- Если пользователь просит более широкий результат, чем позволяет видимый API, реализуй самый узкий безопасный вариант через видимый контракт или верни структуру, которую можно построить без новых контрактов; не придумывай получение всех сущностей.
- Не считай доступ к `__dict__` безопасным способом превратить объект/model в dict. Если contract-функция возвращает объект, model или dataclass-like значение, формируй dict явно по видимым полям, атрибутам, constructor keyword names или явно видимому helper; используй `__dict__` только если project context прямо показывает, что этот тип его поддерживает.
- Если обязательный аргумент contract symbol нельзя получить из параметров нового symbol, локальных переменных, target context или явно видимого проектного контекста, не подставляй придуманный литерал-заглушку вроде общей строки или условного значения; вместо этого измени сигнатуру нового symbol так, чтобы нужный аргумент был передан вызывающим кодом, или выбери другой видимый контракт.
- Если contract context показывает существующий caller для того же production symbol, сначала адаптируй видимый calling pattern этого caller: перенеси необходимые параметры в новый symbol и передавай их в production call. Не заменяй такие параметры фиктивными константами, общими строками, None или агрегирующими значениями, если они не указаны пользователем явно.
- Все текстовые значения JSON пиши на русском языке.
- Для замены существующего symbol используй только "replace_symbol".
- Если передан блок "Сохраняемые элементы текущей реализации", используй его как защищенный ориентир для replace_symbol: сохрани перечисленные элементы и их порядок, если пользовательский запрос явно не требует изменить именно их. Новые действия вставляй до первого использования значения, которое они обновляют.
- Для вставки нового symbol после anchor-symbol используй только "insert_after_symbol".
- Поля insert_scope, expected_new_symbol_kind, parent_qualname обязательны для insert_after_symbol.
- Всегда возвращай import_changes как JSON-массив; если новые imports не нужны, верни [].
- Не добавляй import-строки внутрь поля code.
- Если используешь квалифицированное имя модуля, например `module.function(...)`, верни `add_import` для модуля и используй это же квалифицированное имя в code. Не возвращай `add_from_import` для отдельной функции, если в code используется имя модуля.
- Если возвращаешь `add_from_import`, используй импортированное имя напрямую в code; не оставляй такой import неиспользуемым.
- Если имя уже перечислено в блоке "Доступные imports и имена целевого файла", используй это имя без добавления import_changes.
- Если имя уже доступно в целевом файле через обычный import, guarded import, assignment, class или function definition, используй это имя без повторного import_changes. Если имя нужно только для необязательной локальной аннотации и запрос не требует сохранить эту аннотацию, можно убрать аннотацию вместо добавления неподтвержденного внешнего import.
- Если запрос прямо просит изменить, заменить, добавить или удалить путь импорта, выполняй это через import_changes, даже если имя уже доступно в целевом файле через старый import. Для замены пути импорта удали старый видимый import и добавь новый подтвержденный import. Если тело target-symbol менять не нужно, сохрани его поведение без смысловых изменений.
- Если запрос описывает, что установленная зависимость, пакет, библиотека или компонент не распознается приложением, и в полном файле виден защитный import с fallback на None для этого имени, сначала рассматривай изменение существующего import через import_changes. Не переноси такой import внутрь метода и не меняй логику инициализации, если задача решается заменой пути подключения.
- Если сгенерированный code использует имя, которого нет среди существующих imports или definitions целевого файла, верни нужный import в import_changes. Это относится к именам в теле функции, type annotations, default values, decorators, context managers и helper calls.
- Если неизвестное имя является явно видимым проектным символом из контекста, связанным символом, проектным контрактом, стандартной библиотекой или явно указанной пользователем сущностью с понятным модулем, верни import_changes для этого существующего символа. Не считай такой import новым проектным контрактом. Если путь импорта не подтвержден контекстом, не придумывай его.
- Если после изменения явно видимый импорт на уровне файла больше не нужен и мешает выполнению запроса, попроси удалить его через import_changes. Для строки `import package.module` используй {{"action": "remove_import", "module": "package.module"}}. Для строки `from package import name` используй {{"action": "remove_from_import", "module": "package", "names": ["name"]}}. Удаляй только импорт, который виден в исходном файле.

- Для project symbol используй только точный module path, явно видимый в контексте рядом с этим symbol: qualname, module_name, file_path, import context или source excerpt. Не преобразуй путь по аналогии, не заменяй его на общие модули вроде `models`, `utils`, `schemas`, `helpers` без прямого подтверждения в контексте.
- Если несколько нужных project symbols видны в одном и том же module_name, можно импортировать их из этого module_name одним `add_from_import`. Имена в `names` должны совпадать с фактически видимыми именами symbols.
- Если создаешь проектную модель, DTO, dataclass-like объект или result-object, используй только явно видимые constructor fields / keyword names из model surfaces, source excerpt или сигнатуры `__init__`. Не заменяй их близкими по смыслу alias-именами и не переименовывай аргументы из пользовательского запроса.
- Если исходный запрос явно требует вернуть или создать конкретный result/model object, не заменяй его на `dict`, `list[dict]` или похожую структуру. Исправляй constructor keywords по видимым полям этой модели.
- Не полагайся на from __future__ import annotations как причину пропустить import для явно использованного annotation type. Если используешь внешний тип в сигнатуре, добавь import_changes.
- Используй только imports, реально необходимые для сгенерированного code. Не добавляй запасные imports.
- Пример add_from_import: {{"action": "add_from_import", "module": "pathlib", "names": ["Path"]}}.
- Пример add_import: {{"action": "add_import", "module": "json"}}.
- Пример remove_import: {{"action": "remove_import", "module": "win32com.client"}}.
- Пример remove_from_import: {{"action": "remove_from_import", "module": "win32com", "names": ["client"]}}.
- Меняй только указанный target.
- Не добавляй внешние зависимости.
- Не делай лишний рефакторинг.
- Сохраняй стиль существующего кода.
- Строго следуй исходному запросу пользователя, explicit_requirements и planner_json.
- Для insert_after_symbol создавай новый symbol с уникальным именем: не используй имя уже существующего function/class/method из module outline, class members, target source или full file source, если пользователь явно не просит заменить этот symbol.
- Не придумывай новые сущности, import path, поля, методы, параметры и архитектуру без опоры на контекст.
- Если пользователь явно указал имя метода, функции, класса, параметра, поля или формат строки результата, используй это значение буквально; не заменяй его похожим или более удобным именем.
- Reference artifacts и planner intent не имеют приоритета над явно указанными именами, сигнатурами и литералами из пользовательского запроса.
- Если planner_json, старый docstring, target source или related symbols противоречат исходному запросу пользователя, используй исходный запрос пользователя как источник истины. Не переноси устаревшие формулировки старого docstring в итоговое поведение.
- Если в запросе есть блок Явные требования запроса к результату и литералам, перед возвратом ответа проверь, что наблюдаемое поведение code выполняет эти требования: возвращаемое значение, формат строки, обязательные литералы, имена и суффиксы/префиксы должны соответствовать пользовательскому запросу, а не старому docstring или planner wording.
- Сначала опирайся на код проекта. Связанные production-контракты из contract context считай частью фактического проектного контекста: используй их сигнатуры, import path и source excerpt как источник истины для вызовов соседних компонентов. Если вызываешь symbol из contract context, не опускай обязательные аргументы из его сигнатуры. Reference artifacts используй только как вторичный ориентир.
- Перед возвратом ответа проверь, что поле code само по себе является валидным Python-кодом для данного symbol.
- Если изменяешь строковое выражение, вся итоговая текстовая пунктуация должна находиться внутри строкового литерала или f-строки; после завершения выражения не должно оставаться лишних символов.

Правила для replace_symbol:
- Верни полный обновленный код существующего symbol.
- Если пользовательский запрос требует сохранить существующую структуру или формат, выполняй минимальное изменение: сохраняй порядок видимых действий, helper-вызовы, аргументы, присваивания, ключи данных и форму return, кроме строк, которые прямо нужно изменить.
- Если target_symbol является методом или функцией, поле code должно содержать ровно один def/async def: сам заменяемый target symbol. Не добавляй рядом с ним второй метод, свободную функцию, обработчик, helper, class или другой symbol. Не объявляй внутри него вложенные def/class/helper-symbols. Вспомогательную логику реализуй прямо в теле target symbol через локальные переменные, lambda, setattr, словари, циклы и выражения либо через уже видимый проектный контракт.
- Если при replace_symbol одного метода нужен простой callback/обработчик, не создавай новый метод-обработчик и не подключай сигнал к `self.<новый_метод>`, если этот метод не виден в списке методов класса. Для простого изменения состояния используй lambda/setattr или уже видимый метод класса.
- Если для поведения кажется удобным новый обработчик или helper-метод, но операция — replace_symbol одного метода, не создавай этот новый метод. Встрой минимальную логику в заменяемый метод или используй уже существующий видимый метод.
- Если target_symbol является class, поле code должно содержать полное новое определение этого же класса с тем же именем.
- Нельзя вместо замены класса возвращать только top-level helper-функции, свободные функции или отдельные методы, даже если они реализуют часть требуемого поведения.
- Если пользователь просит, чтобы модель или класс умели выполнять действие, добавляй это поведение внутрь класса как методы или поля класса, если пользователь явно не попросил свободные функции.
- Не заменяй class-target набором внешних функций вида *_to_dict, *_from_dict или похожими helper-функциями, если пользователь явно не попросил такой API.
- Не меняй внешний контракт без явного требования.
- Если заменяешь класс, сохрани поведение существующих публичных методов, если пользователь явно не просил изменить или удалить их.
- Не удаляй и не ослабляй наблюдаемое поведение существующего публичного метода только потому, что новый запрос не повторил это поведение явно.
- Если в исходном публичном методе были проверки предусловий, обработка некорректных входных данных, документированные исключения или иные защитные ветки, сохрани эквивалентное наблюдаемое поведение, если пользователь явно не просил изменить его.
- Если передан блок Required class members, обязательно сохрани все required=true методы; методы с NotImplementedError нужно реализовать, а не удалять.

Правила для insert_after_symbol при insert_scope=module_body:
- Верни только полный код нового top-level function или class.
- Поле insert_after заполни anchor qualname.
- Не меняй код anchor-symbol.
- Поле code должно начинаться сразу с class или def.
- Не добавляй import в code; если нужны imports, верни import_changes.
- Если новый class или function без docstring, добавь короткий docstring на русском языке.

Правила для insert_after_symbol при insert_scope=class_body:
- Верни только код нового метода класса parent_qualname.
- Не возвращай class целиком.
- Не возвращай top-level function.
- Поле code должно начинаться с def/async def или с decorator-строк перед методом, например @property. Внешний отступ класса можно не добавлять.
- Если используешь decorator, decorator и следующий def/async def должны быть на одном базовом уровне отступа. Не пиши @property без отступа, а def с дополнительным отступом.
- Для @property техническое поле expected_new_symbol_kind оставляй "method".
- Используй self, если метод обращается к состоянию класса.
- Не меняй существующие методы и anchor-symbol.
- Если новый method без docstring, добавь короткий docstring на русском языке.
- Если нужны imports в файле, верни import_changes, а не import-строки в code.

Дополнительные семантические правила:
- Если пользователь просит dataclass-модель или dataclass-сущность, новый class обязан быть dataclass.
- Если просят только описание модели, не добавляй лишнюю логику, методы и валидацию.
- Если сгенерированный код обращается к состоянию класса через `self`, используй только явно видимые атрибуты этого класса из исходного кода целевого символа, контекста класса/модуля, разрешенной поверхности API или документированных атрибутов. Не создавай похожие alias-поля и варианты с подчеркиванием для уже существующих публичных атрибутов; например, если виден `self.value`, не используй `self._value`.
- Если у видимого класса уже есть атрибут вспомогательного объекта или зависимости, вызывай методы через этот видимый путь доступа. Не придумывай новый путь доступа к той же зависимости.
- Не используй значение как объект другого типа, если это не следует из видимого проектного контекста. Операции над значениями должны соответствовать их видимому типу. Если нужное преобразование или операция не подтверждены контекстом, используй видимый атрибут текущего класса, видимый метод вспомогательного объекта или явно видимый проектный контракт.
- При вызове видимого метода, функции или проектного контракта соблюдай его видимую сигнатуру: порядок, количество и смысл аргументов. Не заменяй объект аргумента заранее вычисленной строкой или другим представлением, если сигнатура ожидает исходный объект или значение другого типа.
- Если создаешь проектную модель или доменный объект из словаря, JSON, записи хранилища, строки файла, ответа сервиса или другого сериализованного источника, значения конструктора должны соответствовать видимым типам полей модели. Не передавай сырые сериализованные значения в поля с непримитивным типом; сначала явно восстанови значение нужного типа видимым проектным или стандартным способом. Если сериализованное значение отсутствует, а у поля модели есть видимое значение по умолчанию, не передавай это поле в конструктор; дай модели применить свой default.
- Если вызываешь видимый проектный helper или контракт, используй его видимую сигнатуру. Не передавай именованные аргументы, которых нет в видимой сигнатуре или фрагменте исходного кода.
- Если целевой код работает с доменным объектом, используй только явно видимые атрибуты этого объекта.
