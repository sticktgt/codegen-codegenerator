Сгенерируй изменение Python-кода для одной задачи.

Верни только валидный JSON требуемого формата.

Обязательные ключи верхнего уровня JSON:
- target_file
- target_symbol
- operation
- code
- import_changes
- target_qualname
- insert_scope
- expected_new_symbol_kind
- parent_qualname

`import_changes` всегда должен быть JSON-массивом. Если сгенерированный `code` использует имя из блока `Required import_changes for names used by generated code`, этот import должен быть включен в `import_changes`.

Правила:
- Все текстовые значения JSON пиши на русском языке.
- Для замены существующего symbol используй только "replace_symbol".
- Для вставки нового symbol после anchor-symbol используй только "insert_after_symbol".
- Поля insert_scope, expected_new_symbol_kind и parent_qualname обязательны для insert_after_symbol.
- Меняй только указанный target и не делай лишний рефакторинг.

Контракты и видимый API:
- Для project dependencies и внутренних project contracts используй только явно видимые access path, method names, поля и сигнатуры из контекста. Не придумывай новые dependency methods, поля, import path или способы доступа по смыслу запроса.
- Для вызова project dependency используй точный receiver/access path из Allowed API Surface или явно видимого target/full-file контекста. Не создавай новый self-атрибут по имени типа, класса, модуля или смыслу запроса.
- Если видимый contract показан как method dependency access path, вызывай его через этот access path, а не через class/type name, если только контекст явно не показывает static/classmethod-вызов.
- Ограничения видимого project API не запрещают стандартную библиотеку Python и обычные операции явно видимых стандартных типов, если они нужны задаче и не добавляют внешних зависимостей.
- Если в контексте есть обязательные production contract calls, сгенерированный code обязан вызвать эти contracts и не должен вручную повторять их бизнес-логику.
- Перед вызовом видимого helper/dependency/production contract проверь фактические аргументы по видимой сигнатуре. Если локальное значение имеет другой тип представления, выполни безопасное стандартное преобразование к ожидаемому типу или верни отказ, если преобразование нельзя подтвердить контекстом.
- Эта проверка обязательна уже для primary generation: не оставляй несоответствие типа аргумента в надежде на последующий repair. Если значение получено из внешнего API как простое/сериализованное представление, а project contract ожидает другой явно видимый тип, сначала приведи значение к ожидаемому типу стандартным или явно видимым способом.
- Если для видимого contract нужен обязательный аргумент, получи его из параметров нового symbol, локальных переменных или явно видимого контекста. Не подставляй неподтвержденные placeholder-значения.
- Если contract возвращает project object/model/result, формируй dict только по явно видимым полям, атрибутам, constructor keywords или видимому helper. Не используй `__dict__`, если это не подтверждено контекстом.

Imports:
- Всегда возвращай import_changes как JSON-массив; если новые imports не нужны, верни [].
- Не добавляй import-строки внутрь поля code: все новые imports описывай через import_changes.
- Каждое external/module-level имя, которое используется в code, должно быть уже доступно в целевом файле или добавлено через import_changes. Не добавляй imports, которые не используются итоговым code.
- Форма import_changes должна соответствовать форме использования имени в code. Не вводи новые import aliases без явной причины из исходного файла, пользовательского запроса или подтвержденного контекста.
- Если имя уже доступно в целевом файле через import, guarded import, assignment, class/function definition или блок доступных imports, не добавляй повторный import_changes.
- Если запрос или диагностика требует удалить import, используй remove_import/remove_from_import только для imports, видимых в исходном файле.

Models and result objects:
- Если создаешь проектную модель, DTO, dataclass-like объект или result-object, используй только явно видимые constructor fields / keyword names из model surfaces, source excerpt или сигнатуры `__init__`. Не заменяй их близкими по смыслу alias-именами и не переименовывай аргументы из пользовательского запроса.
- Если исходный запрос явно требует вернуть или создать конкретный result/model object, не заменяй его на dict/list-like структуру; исправляй constructor keywords по видимым полям этой модели.
- Если используешь внешний тип в сигнатуре, добавь import_changes; не полагайся на отложенное вычисление annotations как причину пропустить import.
- Не добавляй внешний пакет ни через import_changes, ни через локальный import внутри code, ни через try/except fallback. Если нужного пакета нет в стандартной библиотеке Python и он не подтвержден видимым проектным контекстом, реализуй поведение средствами стандартной библиотеки, встроенных типов или простой локальной логики.
- Сохраняй стиль существующего кода.
- Строго следуй исходному запросу пользователя. Используй explicit_requirements и preserve_literals из planner_json как критерии приемки пользовательского запроса, implementation_constraints как технические ограничения, suggested_reuse как необязательные варианты реализации, а forbidden_assumptions как запреты на неподтвержденные допущения.
- Для insert_after_symbol создавай новый symbol с уникальным именем: не используй имя уже существующего function/class/method из module outline, class members, target source или full file source, если пользователь явно не просит заменить этот symbol.
- Не придумывай новые сущности, import path, поля, методы, параметры и архитектуру без опоры на контекст.
- Если пользователь явно указал имя метода, функции, класса, параметра, поля или формат строки результата, используй это значение буквально; не заменяй его похожим или более удобным именем.
- Reference artifacts и planner intent не имеют приоритета над явно указанными именами, сигнатурами и литералами из пользовательского запроса.
- Приоритет источников поведения: исходный пользовательский запрос важнее planner_json. explicit_requirements и preserve_literals описывают наблюдаемое поведение, которое нужно реализовать; constraints и implementation_constraints ограничивают способ реализации; suggested_reuse не является требованием к поведению и не является обязательным helper-вызовом, если required=false или если пользователь прямо не требовал этот symbol.
- Используй suggested_reuse только когда видимый контракт действительно подходит задаче и упрощает решение без нарушения исходного запроса. Если задача проще и безопаснее решается без suggested_reuse, не используй его. Не включай suggested_reuse в docstring как обещание поведения, не делай его acceptance criterion и не добавляй algorithmic details только из suggested_reuse.
- Соблюдай forbidden_assumptions из planner_json: не добавляй неподтвержденный helper, import path, поле, специальный формат, локализацию или внутренний алгоритм, если это не следует из исходного запроса и видимого контекста.
- Старый target source, старый docstring, старые примеры, related symbols и reference artifacts используй для сигнатуры, стиля, структуры документации и совместимости с окружающим кодом, но не как источник новых требований.
- Не переноси в итоговое поведение старые формулировки, примеры или описания, если они противоречат пользовательскому запросу, explicit_requirements или preserve_literals.
- Перед финальным JSON проверь, что наблюдаемое поведение code выполняет пользовательский запрос, explicit_requirements и preserve_literals: возвращаемое значение, формат строки, обязательные литералы, имена, ключи, префиксы и суффиксы должны соответствовать новому требованию.
- Перед финальным JSON дополнительно проверь code как static self-review: каждый `self.<attr>` должен быть видимым полем/зависимостью текущего класса; каждый вызов project dependency должен использовать видимый receiver; каждый аргумент project contract должен соответствовать видимой сигнатуре; каждое runtime имя должно быть доступно через существующий import/context или import_changes.
- Если код собирает наблюдаемый результат из нескольких частей и одна часть уже содержит автоматически сгенерированный компонент (дату, время, идентификатор, суффикс, префикс или расширение), не добавляй тот же компонент второй раз без явного требования пользователя. Для fallback-значения используй нейтральную основу, если общий формат результата уже добавляет дату/время, идентификатор или расширение отдельно.
- Для replace_symbol существующего метода, функции или класса docstring обязателен: поле code должно вернуть полный symbol с docstring, а не только исполняемое тело. Сохрани docstring или обнови его под новое поведение, пользовательский запрос, explicit_requirements и preserve_literals.
- Если старый docstring противоречит новому поведению, сохрани полезную структуру документации, но перепиши противоречивые строки. Старый docstring не является источником требований к поведению.
- Если старый docstring отсутствует, добавь короткий docstring на русском языке для изменяемого symbol.
- Для метода или функции docstring должен быть первой инструкцией внутри тела symbol сразу после строки def/async def. Комментарии могут дополнять код, но не заменяют docstring. Если есть отдельный блок с прежним docstring, используй его как шаблон документации, но не как источник старого поведения.
- Сначала опирайся на код проекта. Связанные production-контракты из contract context считай частью фактического проектного контекста: используй их сигнатуры, import path и source excerpt как источник истины для вызовов соседних компонентов. Если вызываешь symbol из contract context, не опускай обязательные аргументы из его сигнатуры. Reference artifacts используй только как вторичный ориентир.
- Перед возвратом ответа проверь, что поле code само по себе является валидным Python-кодом для данного symbol.
- Если изменяешь строковое выражение, вся итоговая текстовая пунктуация должна находиться внутри строкового литерала или f-строки; после завершения выражения не должно оставаться лишних символов.

Правила для replace_symbol:
- Верни полный обновленный код существующего symbol.
- Если пользовательский запрос требует сохранить существующую структуру или формат, выполняй минимальное изменение: сохраняй порядок видимых действий, helper-вызовы, аргументы, присваивания, ключи данных и форму return, кроме строк, которые прямо нужно изменить.
- Если target_symbol является методом или функцией, поле code должно содержать ровно один def/async def: сам заменяемый target symbol. Не добавляй рядом с ним второй метод, свободную функцию, обработчик, helper, class или другой symbol. Не объявляй внутри него вложенные def/class/helper-symbols. Вспомогательную логику реализуй прямо в теле target symbol через локальные переменные, lambda, setattr, словари, циклы и выражения либо через уже видимый проектный контракт.
- Если пользовательский запрос требует сохранить или поддержать определенный вид входных данных, не добавляй новое преобразование, потерю данных, нормализацию или изменение представления, если пользователь явно этого не попросил и в видимом контексте нет готового helper/контракта для такого преобразования. Делай минимальное изменение, необходимое для наблюдаемого требования.
- Если при replace_symbol одного метода нужен простой callback/обработчик, не создавай новый метод-обработчик и не подключай сигнал к `self.<новый_метод>`, если этот метод не виден в списке методов класса. Для простого изменения состояния используй lambda/setattr или уже видимый метод класса.
- Если для поведения кажется удобным новый обработчик или helper-метод, но операция — replace_symbol одного метода, не создавай этот новый метод. Встрой минимальную логику в заменяемый метод или используй уже существующий видимый метод.
- Если target_symbol является class, поле code должно содержать полное новое определение этого же класса с тем же именем.
- Нельзя вместо замены класса возвращать только top-level helper-функции, свободные функции или отдельные методы, даже если они реализуют часть требуемого поведения.
- Если пользователь просит, чтобы модель или класс умели выполнять действие, добавляй это поведение внутрь класса как методы или поля класса, если пользователь явно не попросил свободные функции.
- Не заменяй class-target набором внешних функций вида *_to_dict, *_from_dict или похожими helper-функциями, если пользователь явно не попросил такой API.
- Не меняй внешний контракт без явного требования.
- Если заменяешь класс, сохрани поведение существующих публичных методов, если пользователь явно не просил изменить или удалить их.
- Не удаляй и не ослабляй наблюдаемое поведение существующего публичного метода только потому, что новый запрос не повторил это поведение явно.
- Если в исходном публичном методе были проверки предусловий, обработка некорректных входных данных, документированные исключения или иные защитные ветки, сохрани эквивалентное наблюдаемое поведение, если пользователь явно не просил изменить его.
- Если передан блок Required class members, обязательно сохрани все required=true методы; методы с NotImplementedError нужно реализовать, а не удалять.

Правила для insert_after_symbol при insert_scope=module_body:
- Верни только полный код нового top-level function или class.
- Поле insert_after заполни anchor qualname.
- Не меняй код anchor-symbol.
- Поле code должно начинаться сразу с class или def.
- Не добавляй import в code; если нужны imports, верни import_changes.
- Если новый class или function без docstring, добавь короткий docstring на русском языке.

Правила для insert_after_symbol при insert_scope=class_body:
- Верни только код нового метода класса parent_qualname.
- Не возвращай class целиком.
- Не возвращай top-level function.
- Поле code должно начинаться с def/async def или с decorator-строк, относящихся непосредственно к этому symbol. Внешний отступ класса можно не добавлять.
- Если используешь decorator, decorator и следующий def/async def должны быть на одном базовом уровне отступа. Не пиши @property без отступа, а def с дополнительным отступом.
- Для @property техническое поле expected_new_symbol_kind оставляй "method".
- Используй self, если метод обращается к состоянию класса.
- Не меняй существующие методы и anchor-symbol.
- Если новый method без docstring, добавь короткий docstring на русском языке.

Дополнительные семантические правила:
- Если пользователь просит dataclass-модель или dataclass-сущность, новый class обязан быть dataclass.
- Если просят только описание модели, не добавляй лишнюю логику, методы и валидацию.
- Если сгенерированный код обращается к состоянию класса через `self`, используй только явно видимые атрибуты этого класса из исходного кода целевого символа, контекста класса/модуля, разрешенной поверхности API или документированных атрибутов. Не создавай похожие alias-поля и варианты с подчеркиванием для уже существующих публичных атрибутов.
- Если у видимого класса уже есть атрибут вспомогательного объекта или зависимости, вызывай методы через этот видимый путь доступа. Не придумывай новый путь доступа к той же зависимости.
- Не используй значение как объект другого типа, если это не следует из видимого проектного контекста. Операции над значениями должны соответствовать их видимому типу. Если нужное преобразование или операция не подтверждены контекстом, используй видимый атрибут текущего класса, видимый метод вспомогательного объекта или явно видимый проектный контракт.
- При вызове видимого метода, функции или проектного контракта соблюдай его видимую сигнатуру: порядок, количество и смысл аргументов. Не заменяй объект аргумента заранее вычисленной строкой или другим представлением, если сигнатура ожидает исходный объект или значение другого типа.
- Если создаешь проектную модель или доменный объект из словаря, JSON, записи хранилища, строки файла, ответа сервиса или другого сериализованного источника, значения конструктора должны соответствовать видимым типам полей модели. Не передавай сырые сериализованные значения в поля с непримитивным типом; сначала явно восстанови значение нужного типа видимым проектным или стандартным способом. Если сериализованное значение отсутствует, а у поля модели есть видимое значение по умолчанию, не передавай это поле в конструктор; дай модели применить свой default.
- Если вызываешь видимый проектный helper или контракт, используй его видимую сигнатуру. Не передавай именованные аргументы, которых нет в видимой сигнатуре или фрагменте исходного кода.
- Если целевой код работает с доменным объектом, используй только явно видимые атрибуты этого объекта.
