Сгенерируй один pytest-файл для проверки измененного или добавленного Python-функционала.

Верни только валидный JSON.

Обязательные поля JSON:
- test_file
- code

Правила:
- Разрешены только pytest и стандартная библиотека Python.
- Не добавляй новые зависимости проекта.
- Верни полный текст тестового файла.
- Используй точное значение test_file, указанное ниже.
- Не добавляй markdown fences.
- Верни самодостаточный pytest-файл со всеми необходимыми import.
- Импортируй тестируемый symbol из target_file и используй target_symbol.
- Для operation=insert_after_symbol target_symbol уже указывает на новый symbol, который нужно тестировать; не строй тест вокруг anchor-symbol.
- Если insert_scope=class_body, target_symbol указывает на новый метод класса: импортируй parent class, создай экземпляр и вызывай метод через этот экземпляр; не импортируй метод как top-level function.
- Если target_symbol указывает на class, импортируй и тестируй этот class.
- Если target_symbol указывает на function, импортируй и тестируй эту function.
- Используй только те классы, функции, поля, атрибуты, пути импорта и аргументы конструктора, которые явно видны в доступном проектном контексте.
- Не придумывай новые поля dataclass, аргументы __init__, атрибуты объектов, имена параметров и пути импорта.
- Если в связанных тестах уже показан способ создания или использования проектного объекта, считай этот паттерн основным источником истины и повторяй его максимально близко, особенно для пути импорта, имени модуля, набора аргументов конструктора и имен параметров.
- Если target-код, связанные тесты и другой проектный контекст дают разные сигналы, отдавай приоритет более надежному проектному контексту в таком порядке: связанные тесты, полный исходник файла, явные import и сигнатуры, и только потом target-код.
- Для импорта проектных символов используй только тот путь модуля, который явно присутствует в доступном проектном контексте. Не нормализуй, не сокращай, не переименовывай и не заменяй путь по аналогии или догадке.
- Если контекста недостаточно, строй самый узкий позитивный тест на реально видимое поведение без догадок.
- Не определяй production-логику внутри тестового файла.
- Импортируй pytest только если он реально используется; если используется pytest.raises или pytest.*, обязательно добавь import pytest.
- Для bool-результата используй только `assert expression` или `assert not expression`; не используй сравнения с True или False.
- Тест должен проходить pytest и не содержать очевидных проблем с import.
- Ожидаемые имена symbols, параметры и строки результата бери из исходного запроса и explicit requirements. Если generated target-код противоречит этим требованиям, не подменяй требования поведением generated code.
- Не придумывай поведение, которого нет в target-коде, связанных тестах, полном исходнике файла или явных требованиях.
- Для dataclass без собственной логики по умолчанию достаточно одного узкого позитивного теста на создание экземпляра и значения полей.
- Негативные тесты добавляй только если они прямо следуют из переданного контекста.
- План теста ниже обязателен к исполнению, если он не противоречит более надежному проектному контексту.
- Если target_symbol импортирован, он должен реально использоваться в тесте — либо в вызове, либо в создании экземпляра, либо в assert-проверке результата.
- Если тест создает экземпляр проектного класса или dataclass, передавай только те аргументы конструктора, которые явно видны в доступном контексте.
- Если в related tests или full file source уже есть пример создания того же класса, повторяй этот вызов максимально близко, включая обязательные аргументы конструктора.
- Если обязательность аргумента неясна, не придумывай минимальный конструктор; вместо этого опирайся на related tests или full file source.
- Для проектных моделей не проверяй конструктор на минимальном наборе аргументов, если в контексте уже есть рабочий пример создания такого объекта.
- Если тест создает экземпляр проектной модели, повторяй полный валидный конструктор из related tests или другого явного проектного контекста. Не выбрасывай обязательные аргументы и не пытайся строить "минимальный" объект по догадке.
