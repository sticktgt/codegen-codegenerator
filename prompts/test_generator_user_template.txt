Сгенерируй один pytest-файл для проверки измененного или добавленного Python-функционала.

Верни только валидный JSON.

Обязательные поля JSON:
- test_file
- code

Правила:

1. Общий контракт ответа
- Верни полный самодостаточный pytest-файл со всеми необходимыми import.
- Используй точное значение test_file, указанное ниже.
- Не добавляй markdown fences.
- Разрешены только pytest, стандартная библиотека Python и явно видимые project symbols.
- Импортируй pytest только если он реально используется.
- Не добавляй новые зависимости проекта и optional pytest plugin fixtures. По умолчанию создавай test-функции без fixture-параметров; встроенные pytest fixtures используй только когда они прямо нужны.

2. Источники истины
- Если передан сгенерированный target-код, именно он является главным источником проверяемого поведения.
- Если в запросе есть блок Explicit request output and literal obligations, ожидаемые значения теста должны сохранять эти требования. Не бери ожидаемый формат из старого docstring или старого source, если он противоречит явному CR.
- Справочный исходный файл до изменения используй для импортов, стиля, конструктора parent class и старых публичных контрактов, но не для переопределения поведения target-кода.
- Related tests используй только если они переданы и не противоречат target-коду, model surfaces, source excerpt или видимым сигнатурам.
- Если generated target-код противоречит явным требованиям пользователя, не подменяй требования поведением generated code.

3. Импорты и project symbols
- Для project symbol используй только точный module path, явно видимый рядом с этим symbol: qualname, module_name, file_path, import context, source excerpt или Required project imports.
- Если передан блок Required project imports, используй эти import paths для соответствующих symbols и не заменяй их похожими путями вроде `*.models`, `*.utils`, `*.search_result` или `*.search_utils` без прямого подтверждения.
- Тестовый файл должен быть самодостаточным: каждое используемое имя должно быть импортировано, определено локально, передано как параметр тестовой функции или быть builtin-именем. Если используешь symbol из стандартной библиотеки или проекта, добавь явный import в начало теста.
- Если используешь project class, function, dataclass или helper в тесте, он должен быть явно импортирован из видимого project module или локально определен как fake/stub; не используй неимпортированные имена.
- Не импортируй методы класса как top-level functions. Для class_body method импортируй parent class и вызывай метод через экземпляр.
- Если target_symbol импортирован, он должен реально использоваться в вызове, создании экземпляра или assert-проверке результата.

4. Создание проектных объектов
- Создавай project class/model только через видимый конструктор или через явно показанный в проектном контексте способ создания.
- Передавай все обязательные аргументы конструктора и только те keyword-аргументы, которые видны в сигнатуре, model surfaces, source excerpt или related/context source.
- Значения аргументов должны быть совместимы с видимыми типами. Не заменяй типизированные аргументы строками, None или произвольными заглушками, если в контексте виден более точный тип.
- Если сигнатура конструктора неясна, используй явно показанный project-context пример; если такого примера нет, строй самый узкий тест через fake/stub вместо создания непонятного project object.
- Если передан recommended setup для parent instance, используй его как основной способ создания объекта; не заменяй его строковыми заглушками, `None`, `__new__` или произвольным минимальным конструктором.
- Метаданные CR вроде `Title:` не являются полями модели и не дают права использовать constructor keyword `title`, если он не виден в model surfaces.
- Не создавай экземпляр project class через `__new__`, если виден обычный конструктор `__init__`; не вызывай project class без обязательных аргументов.
- Если для обязательного параметра нужен простой ресурс или значение, создай минимальное тестовое значение средствами стандартной библиотеки, встроенной pytest fixture или явно видимого проектного контекста. Если для этого используется имя из стандартной библиотеки, импортируй его явно в тестовом файле.

5. Управление зависимостями и helper-вызовами
- Если target-код вызывает helper того же экземпляра через `self.<helper>(...)`, контролируй этот видимый helper через instance-level fake/lambda с той же сигнатурой вызова.
- Если target-код получает данные через видимый helper/dependency, а тест подменяет этот источник через fake/stub/lambda/monkeypatch, эта подмена является достаточной подготовкой данных. Не вызывай дополнительно persistence/storage/repository/save/load/create/update методы и не создавай скрытое состояние объекта (`_items`, `_notes`, `_storage`, `_records`), если target-код сам не вызывает эти методы и они не нужны для проверяемого поведения.
- Не подменяй свободную helper-функцию в исходном модуле helper-а, если target-код использует direct import этой функции. Используй реальный helper и вычисляй expected values через него, либо patch binding в модуле target-кода.
- Не вызывай методы project object, которых нет в видимом class source/full file/source excerpt.
- Если нужен helper/dependency, используй только видимый способ его получения: существующий атрибут экземпляра, явно видимый конструктор или локальный fake/stub. Не добавляй dependency/helper как новый keyword-аргумент конструктора, если такого аргумента нет в видимой сигнатуре.
- Если тест передает fake/stub объект в target-код или production contract, fake/stub должен реализовать все поля/атрибуты, которые этот target/contract source явно читает; не заменяй поля похожими именами.

6. Ожидаемые значения и assert
- Ожидаемые значения assert должны следовать из target-кода, явно заданных данных теста, видимых default-значений модели и видимых helper-функций.
- Если ожидаемый результат зависит от значений по умолчанию в модели, используй видимые default-значения модели, а не придумывай собственные.
- Если тест проверяет модель или доменный объект, восстановленный из JSON, словаря, файла или записи хранилища, ожидаемые значения должны соответствовать видимым типам полей модели, а не сырому сериализованному представлению.
- Если contract-функция возвращает объект/model/dataclass-like значение, не используй `__dict__` как способ превратить его в dict, если project context прямо не показывает, что это поддерживается.
- Для bool-результата используй `assert expression` или `assert not expression`, а не сравнение с True/False.
- Негативные тесты добавляй только если они прямо следуют из target-кода, явных требований или видимого старого публичного поведения.
- Если контекста недостаточно, сгенерируй самый узкий позитивный тест на реально видимое поведение без догадок.

7. Специфика target
- Для operation=insert_after_symbol target_symbol уже указывает на новый symbol, который нужно тестировать; не строй тест вокруг anchor-symbol.
- Если insert_scope=class_body, target_symbol указывает на метод класса: импортируй parent class, создай экземпляр по видимой сигнатуре конструктора и вызывай метод через этот экземпляр.
- Если target_symbol указывает на class, импортируй и тестируй этот class.
- Если target_symbol указывает на function, импортируй и тестируй эту function.
- План теста ниже обязателен к исполнению, если он не противоречит более надежному проектному контексту.
