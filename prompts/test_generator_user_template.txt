Сгенерируй один pytest-файл для проверки измененного или добавленного Python-функционала.

Верни только валидный JSON.

Обязательные поля JSON:
- test_file
- code

Правила:
- Разрешены только pytest и стандартная библиотека Python.
- Не добавляй новые зависимости проекта.
- Верни полный текст тестового файла.
- Используй точное значение test_file, указанное ниже.
- Не добавляй markdown fences.
- Верни самодостаточный pytest-файл со всеми необходимыми import.
- Импортируй тестируемый symbol из target_file и используй target_symbol.
- Для operation=insert_after_symbol target_symbol уже указывает на новый symbol, который нужно тестировать; не строй тест вокруг anchor-symbol.
- Если target_symbol указывает на class, импортируй и тестируй этот class.
- Если target_symbol указывает на function, импортируй и тестируй эту function.
- Используй только те классы, функции, поля, атрибуты и аргументы, которые явно видны в доступном контексте.
- Не придумывай новые поля dataclass, аргументы __init__, атрибуты объектов и имена параметров.
- Если в связанных тестах уже показан способ создания или использования проектного объекта, повторяй этот паттерн максимально близко.
- Если generated target-код, связанные тесты и другой проектный контекст дают разные сигналы, отдавай приоритет более стабильному проектному контексту: связанным тестам, полному исходнику файла и явно видимым import/сигнатурам.
- Если контекста недостаточно, строй самый узкий позитивный тест на реально видимое поведение без догадок.
- Не определяй production-логику внутри тестового файла.
- Импортируй pytest только если он реально используется; если используется pytest.raises или pytest.*, обязательно добавь import pytest.
- Для bool-результата используй только `assert expression` или `assert not expression`; не используй сравнения с True или False.
- Тест должен проходить pytest и не содержать очевидных проблем с import.
- Не придумывай поведение, которого нет в target-коде, связанных тестах, полном исходнике файла или явных требованиях.
- Для dataclass без собственной логики по умолчанию достаточно одного узкого позитивного теста на создание экземпляра и значения полей.
- Негативные тесты добавляй только если они прямо следуют из переданного контекста.
- План теста ниже обязателен к исполнению, если он не противоречит более надежному проектному контексту.
- Если target_symbol импортирован, он должен реально использоваться в тесте — либо в вызове, либо в создании экземпляра, либо в assert-проверке результата.
