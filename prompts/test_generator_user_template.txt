Сгенерируй один pytest-файл для проверки измененного или добавленного Python-функционала.

Верни только валидный JSON.

Обязательные поля JSON:
- test_file
- code

Правила:

1. Общий контракт ответа
- Верни полный самодостаточный pytest-файл со всеми необходимыми import.
- Используй точное значение test_file, указанное ниже.
- Не добавляй markdown fences.
- Разрешены только pytest, стандартная библиотека Python и явно видимые project symbols.
- Импортируй pytest только если он реально используется.
- Не добавляй новые зависимости проекта и optional pytest plugin fixtures. По умолчанию создавай test-функции без fixture-параметров; встроенные pytest fixtures используй только когда они прямо нужны.

2. Источники истины
- Если передан сгенерированный target-код, именно он является главным источником проверяемого поведения.
- Если в запросе есть блок Явные требования запроса к результату и литералам, значения в проверках должны сохранять эти требования.
- Текст документации метода и примеры в нем можно использовать только для понимания назначения метода.
- Не бери из текста документации метода точные значения для проверки, если исполняемый код вычисляет эти значения во время работы.
- Главный источник точных проверяемых значений — явный запрос пользователя, проверяемый код и реально полученный результат выполнения.
- Справочный исходный файл до изменения используй для импортов, стиля, конструктора parent class и старых публичных контрактов, но не для переопределения поведения target-кода.
- Related tests используй только если они переданы и не противоречат target-коду, model surfaces, source excerpt или видимым сигнатурам.
- Если generated target-код противоречит явным требованиям пользователя, не подменяй требования поведением generated code.

3. Импорты и project symbols
- Для project symbol используй только точный module path, явно видимый рядом с этим symbol: qualname, module_name, file_path, import context, source excerpt или Required project imports.
- Если передан блок Required project imports, используй эти import paths для соответствующих symbols и не заменяй их похожими путями вроде `*.models`, `*.utils`, `*.search_result` или `*.search_utils` без прямого подтверждения.
- Тестовый файл должен быть самодостаточным: каждое используемое имя должно быть импортировано, определено локально, передано как параметр тестовой функции или быть builtin-именем. Если используешь symbol из стандартной библиотеки или проекта, добавь явный import в начало теста.
- Если используешь project class, function, dataclass или helper в тесте, он должен быть явно импортирован из видимого project module или локально определен как fake/stub; не используй неимпортированные имена.
- Не импортируй методы класса как top-level functions. Для class_body method импортируй parent class как источник метода. Обычно вызывай метод через экземпляр; если в prompt есть lightweight self strategy для простых self-атрибутов или target-код не использует self, вызывай метод как unbound method через parent class на fake/stub объекте.
- Если target_symbol импортирован, он должен реально использоваться в вызове, создании экземпляра или assert-проверке результата.

4. Создание проектных объектов
- Создавай project class/model только через видимый конструктор или через явно показанный в проектном контексте способ создания.
- Передавай все обязательные аргументы конструктора и только те keyword-аргументы, которые видны в сигнатуре, model surfaces, source excerpt или related/context source.
- Значения аргументов должны быть совместимы с видимыми типами. Не заменяй типизированные аргументы строками, None или произвольными заглушками, если в контексте виден более точный тип.
- Если сигнатура конструктора неясна, используй явно показанный project-context пример; если такого примера нет, строй самый узкий тест через fake/stub вместо создания непонятного project object.
- Если поле project model видно в constructor_fields/model surfaces и тесту нужно начальное значение этого поля, передавай его через keyword-аргумент конструктора. Не присваивай такое поле после создания объекта, если target-код или пользовательский запрос явно не проверяет именно мутацию после создания.
- Если передан recommended setup для parent instance и нет lightweight self strategy, используй его как основной способ создания объекта; не заменяй его строковыми заглушками, `None`, `__new__` или произвольным минимальным конструктором.
- Метаданные запроса вроде `Title:` не являются полями модели и не дают права использовать constructor keyword `title`, если он не виден в model surfaces.
- Не создавай экземпляр project class через `__new__`, если виден обычный конструктор `__init__`; не вызывай project class без обязательных аргументов.
- Если для обязательного параметра нужен простой ресурс или значение, создай минимальное тестовое значение средствами стандартной библиотеки, встроенной pytest fixture или явно видимого проектного контекста. Если для этого используется имя из стандартной библиотеки, импортируй его явно в тестовом файле.
- Если проверяется отдельный метод класса, а его исполняемый target-код не использует `self` или использует только простые `self`-атрибуты и не требует реального конструктора, не создавай тяжелый объект только ради вызова метода. Используй локальный fake/stub объект, `types.SimpleNamespace` или `None` для self, если тело метода не обращается к self, и вызывай метод как unbound method: `ParentClass.target_method(fake_self)`.
- Если запрос явно проверяет запуск файла как точки входа приложения или код с долгим циклом выполнения, не запускай настоящее приложение только ради проверки. Предпочитай безопасную статическую проверку исходного файла через стандартную библиотеку или контролируемые fake/stub зависимости без запуска долгого цикла. Для такой статической проверки не импортируй project symbols, которые нужны только внутри настоящего запуска приложения.
- Если проверяемый код запуска приложения вызывает цикл выполнения и передает его результат в `sys.exit`, не запускай настоящий цикл и не завершай процесс. Используй контролируемые fake/stub зависимости или `monkeypatch` для binding-ов в target-модуле. Задай явное возвращаемое значение fake/stub метода цикла выполнения и проверяй, что `sys.exit` получил именно это значение; не ожидай `0` по умолчанию.
- Если запрос проверяет только поведение одного метода, не расширяй тест до создания настоящего GUI-окна, проверки `windowTitle`, `statusBar`, `toolbar` или других унаследованных GUI-свойств, если это прямо не требуется запросом.

5. Управление зависимостями и helper-вызовами
- Если target-код вызывает helper того же экземпляра через `self.<helper>(...)` и пользовательский запрос не требует сохранить реальный путь выполнения, контролируй этот видимый helper через instance-level fake/lambda с той же сигнатурой вызова.
- Если пользовательский запрос требует сохранить существующую структуру работы target-метода, тест не должен подменять helper-вызовы так, чтобы скрыть неверный аргумент, порядок вызовов или изменение формата данных. В таком случае предпочитай реальный минимальный сценарий с временными ресурсами стандартной библиотеки или встроенными pytest fixtures.
- Если target-код получает данные через видимый helper/dependency, а тест подменяет этот источник через fake/stub/lambda/monkeypatch, эта подмена является достаточной подготовкой данных. Не вызывай дополнительно persistence/storage/repository/save/load/create/update методы и не создавай скрытое состояние объекта (`_items`, `_notes`, `_storage`, `_records`), если target-код сам не вызывает эти методы и они не нужны для проверяемого поведения.
- Не подменяй свободную helper-функцию в исходном модуле helper-а, если target-код использует direct import этой функции. Используй реальный helper и вычисляй expected values через него, либо patch binding в модуле target-кода.
- Не вызывай методы project object, которых нет в видимом class source/full file/source excerpt.
- Если нужен helper/dependency, используй только видимый способ его получения: существующий атрибут экземпляра, явно видимый конструктор или локальный fake/stub. Не добавляй dependency/helper как новый keyword-аргумент конструктора, если такого аргумента нет в видимой сигнатуре.
- Если тест передает fake/stub объект в target-код или production contract, fake/stub должен реализовать все поля/атрибуты, которые этот target/contract source явно читает; не заменяй поля похожими именами.

6. Ожидаемые значения и assert
- Значения в проверках должны следовать из проверяемого кода, явных данных теста, видимых значений по умолчанию и видимых вспомогательных функций.
- Не записывай вручную ожидаемые значения, которые проверяемый код сам вычисляет во время работы.
- Такое значение нужно брать из результата вызова проверяемого метода, из измененного состояния объекта, из созданных данных или через явно видимую вспомогательную функцию.
- Это относится к идентификаторам, именам, датам, статусам, форматированным строкам, фрагментам текста, позициям совпадений, структурам данных и другим значениям, которые получаются из входных данных или состояния программы.
- Если проверяемый метод вернул значение, которое нужно использовать дальше в тесте, используй именно это возвращенное значение. Не собирай такое же значение вручную из отдельных частей.
- Если проверяемый метод создает или сохраняет данные и возвращает значение, сохрани результат вызова в переменную. Для дальнейших проверок сначала используй это возвращенное значение, измененное состояние объекта или публичный метод чтения.
- Не создавай вручную имя, идентификатор, адрес ресурса, ключ, фрагмент текста или другую структуру, которую проверяемый код вычисляет сам.
- Если проверяемый код использует видимую вспомогательную функцию для вычисления значения, тест не должен повторять это вычисление вручную другим способом. Используй результат проверяемого метода или ту же видимую вспомогательную функцию.
- Если проверяемый код получает текущую дату или время во время выполнения, фиксированная дата или время допустимы в ожидаемых значениях только при явной подмене того же источника времени. Без такой подмены проверяй, что полученное значение находится между временем до вызова и временем после вызова.
- Если запрос изменяет существующее поведение или исправляет ошибку, добавь проверку, которая отличает новое требование от прежнего поведения, если прежний код виден в контексте.
- Выбирай такие входные данные, при которых старый и новый варианты поведения дают разный наблюдаемый результат. Не ограничивайся обычным успешным случаем, если он одинаково проходит до и после изменения.
- Для различающей проверки используй минимальные данные: значение на границе, рядом с границей, внутри и вне условия, либо два похожих объекта, которые отличаются только важным для требования признаком.
- Если ожидаемый результат зависит от значений по умолчанию в модели, используй видимые default-значения модели, а не придумывай собственные.
- Если тест проверяет модель или доменный объект, восстановленный из JSON, словаря, файла или записи хранилища, ожидаемые значения должны соответствовать видимым типам полей модели, а не сырому сериализованному представлению.
- Если contract-функция возвращает объект/model/dataclass-like значение, не используй `__dict__` как способ превратить его в dict, если project context прямо не показывает, что это поддерживается.
- Для bool-результата используй `assert expression` или `assert not expression`, а не сравнение с True/False.
- Негативные тесты добавляй только если они прямо следуют из target-кода, явных требований или видимого старого публичного поведения.
- Если контекста недостаточно, сгенерируй самый узкий позитивный тест на реально видимое поведение без догадок.

7. Специфика target
- Для operation=insert_after_symbol target_symbol уже указывает на новый symbol, который нужно тестировать; не строй тест вокруг anchor-symbol.
- Если insert_scope=class_body, target_symbol указывает на метод класса: импортируй parent class как источник метода. Создавай настоящий экземпляр только когда target-код или запрос требует реального конструктора. Если target-код не использует self или его можно проверить через простые self-атрибуты/простые вызовы методов у этих атрибутов, используй fake/stub объект, `types.SimpleNamespace` или `None` для self, если тело метода не обращается к self, и вызывай метод как unbound method.
- Если target_symbol указывает на class, импортируй и тестируй этот class.
- Если target_symbol указывает на function, импортируй и тестируй эту function.
- План теста ниже обязателен к исполнению, если он не противоречит более надежному проектному контексту.
- Если в плане теста есть `avoid`, эти элементы являются запретами для теста: не импортируй их, не создавай их экземпляры, не наследуйся от них, не используй их в аннотациях и не применяй их как базовые классы fake/stub.
- Если для class-method передана lightweight/fake-self стратегия, fake/stub должен быть локальным простым объектом без наследования от parent class и без наследования от GUI/project dependency classes, если сам проверяемый код явно не требует inherited runtime behavior.
