Сгенерируй один pytest-файл для проверки измененного или добавленного Python-функционала.

Верни только валидный JSON.

Обязательные поля JSON:
- test_file
- code

Правила:
- Не считай доступ к `__dict__` безопасным способом превратить объект/model в dict. Если contract-функция возвращает объект, model или dataclass-like значение, формируй dict явно по видимым полям, атрибутам, constructor keyword names или явно видимому helper; используй `__dict__` только если project context прямо показывает, что этот тип его поддерживает.
- Разрешены только pytest и стандартная библиотека Python.
- Блок Allowed API Surface ограничивает проектные зависимости и внутренние проектные контракты. Он не запрещает использовать стандартную библиотеку Python и обычные методы явно видимых стандартных типов в тесте, если это не добавляет внешних зависимостей и соответствует видимому коду.
- Если для подготовки тестовых данных нужен временный файл, директория, коллекция, строка, дата, путь или другой простой объект стандартной библиотеки, используй обычные средства стандартной библиотеки и явно видимые стандартные типы. Не придумывай для этого новые проектные helper-методы или новые аргументы конструктора.
- Не используй optional pytest plugin fixtures: такие зависимости не гарантированы в окружении.
- По умолчанию создавай test-функции без fixture-параметров. Добавляй fixture-параметры только если они явно показаны в связанных тестах или прямо требуются запросом.
- По умолчанию используй простые локальные fake/stub классы и реальные видимые проектные объекты из контекста.
- Если без mock/patch нельзя обойтись, используй только стандартную библиотеку Python; не добавляй новые зависимости проекта.
- Не добавляй новые зависимости проекта.
- Верни полный текст тестового файла.
- Используй точное значение test_file, указанное ниже.
- Не добавляй markdown fences.
- Верни самодостаточный pytest-файл со всеми необходимыми import.
- Если используешь project class, function, dataclass или helper в теле теста, он должен быть явно импортирован из видимого project module или локально определен как fake/stub; не используй неимпортированные имена.
- Импортируй тестируемый symbol из target_file и используй target_symbol.
- Для operation=insert_after_symbol target_symbol уже указывает на новый symbol, который нужно тестировать; не строй тест вокруг anchor-symbol.
- Если insert_scope=class_body, target_symbol указывает на метод класса: импортируй parent class, создай экземпляр по видимой сигнатуре конструктора и вызывай метод через этот экземпляр; не импортируй метод как top-level function.
- Если видимый конструктор project class содержит обязательные параметры без default-значений, передай валидные тестовые значения для всех таких параметров. Не вызывай project class без обязательных аргументов и не выдумывай имена аргументов.
- Если для теста нужен helper/dependency, используй только видимый способ его получения: существующий атрибут экземпляра, явно видимый конструктор или локальный fake/stub. Не добавляй dependency/helper как новый keyword-аргумент конструктора, если такого аргумента нет в видимой сигнатуре.
- Если для обязательного параметра конструктора нужен простой ресурс или значение, создай минимальное тестовое значение средствами стандартной библиотеки или через явно видимый проектный контекст; не используй plugin-specific fixtures и не добавляй зависимости.
- Если target_symbol указывает на class, импортируй и тестируй этот class.
- Если target_symbol указывает на function, импортируй и тестируй эту function.
- Используй только те классы, функции, поля, атрибуты, пути импорта и аргументы конструктора, которые явно видны в доступном проектном контексте.
- Не придумывай новые поля dataclass, аргументы __init__, атрибуты объектов, имена параметров и пути импорта.
- Если тест передает fake/stub объект в target-код или production contract, fake/stub должен реализовать все поля/атрибуты, которые этот target/contract source явно читает; не заменяй поля похожими именами.
- Если передан блок Contract attribute requirements, он является обязательным для test data: объекты соответствующего item_type должны иметь все required_fields. Если используешь реальную project model, передавай только constructor_fields; если нужное required_field не является constructor field, задай его после создания объекта или используй локальный fake/stub.
- Ожидаемые значения assert должны соответствовать фактическому target-коду и явно заданным данным теста; не задавай ожидания, противоречащие default values или условиям, видимым в target/contract source.
- Если тест проверяет модель или доменный объект, восстановленный из JSON, словаря, файла, записи хранилища или другого сериализованного источника, ожидаемые значения должны соответствовать видимым типам полей модели. Не ожидай сырую строку там, где поле модели видно как дата, время, путь, число или вложенный объект; ожидай значение восстановленного типа. Если сериализованное поле отсутствует, а модель имеет значение по умолчанию, тест должен ожидать значение по умолчанию модели, а не None, если None явно не разрешен видимым типом поля.
- Если в связанных тестах уже показан способ создания или использования проектного объекта, считай этот паттерн основным источником истины и повторяй его максимально близко, особенно для пути импорта, имени модуля, набора аргументов конструктора и имен параметров.
- Если contract context содержит production symbol, используй его сигнатуру, import path и source excerpt как явный проектный контракт для вызова или создания связанных объектов. Не закрепляй в тесте вызов такого symbol без обязательных аргументов из его сигнатуры.
- Если передан сгенерированный target-код, именно он является главным источником истины для теста. Связанные тесты, контракты, полный исходник файла и импорты используй для стиля, путей импорта, окружающего кода и старых публичных контрактов, но не для переопределения полей, аргументов конструктора, методов или ключей словаря из сгенерированного target-кода.
- Если сгенерированный target-код и справочный контекст целевого файла до изменения противоречат друг другу, используй сгенерированный target-код для создания тестовых данных и assert-ожиданий.
- Для импорта проектных символов используй только тот путь модуля, который явно присутствует в доступном проектном контексте. Не нормализуй, не сокращай, не переименовывай и не заменяй путь по аналогии или догадке.
- Если контекста недостаточно, строй самый узкий позитивный тест на реально видимое поведение без догадок.
- Не определяй production-логику внутри тестового файла.
- Импортируй pytest только если он реально используется; если используется pytest.raises или pytest.*, обязательно добавь import pytest.
- Для bool-результата используй только `assert expression` или `assert not expression`; не используй сравнения с True или False.
- Тест должен проходить pytest и не содержать очевидных проблем с import.
- Ожидаемые имена symbols, параметры и строки результата бери из исходного запроса и explicit requirements. Если generated target-код противоречит этим требованиям, не подменяй требования поведением generated code.
- Не придумывай поведение, которого нет в target-коде, связанных тестах, полном исходнике файла или явных требованиях.
- Для dataclass без собственной логики по умолчанию достаточно одного узкого позитивного теста на создание экземпляра и значения полей.
- Негативные тесты добавляй только если они прямо следуют из переданного контекста.
- План теста ниже обязателен к исполнению, если он не противоречит более надежному проектному контексту.
- Если target_symbol импортирован, он должен реально использоваться в тесте — либо в вызове, либо в создании экземпляра, либо в assert-проверке результата.
- Если тест создает экземпляр проектного класса или dataclass, передавай только те аргументы конструктора, которые явно видны в доступном контексте, и обязательно покрывай все видимые обязательные параметры конструктора.
- Если в related tests или full file source уже есть пример создания того же класса, повторяй этот вызов максимально близко, включая обязательные аргументы конструктора.
- Если обязательность аргумента неясна, не придумывай минимальный конструктор; вместо этого опирайся на related tests или full file source.
- Для проектных моделей не проверяй конструктор на минимальном наборе аргументов, если в контексте уже есть рабочий пример создания такого объекта.
- Если тест создает экземпляр проектной модели, повторяй полный валидный конструктор из related tests или другого явного проектного контекста. Не выбрасывай обязательные аргументы и не пытайся строить "минимальный" объект по догадке.
