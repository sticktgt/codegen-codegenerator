Сгенерируй простой pytest-тест для уже сгенерированного Python-кода.

Верни только валидный JSON без markdown.

Обязательные ключи JSON:
- test_file
- code

Поле `test_file` должно быть точно равно `{generated_test_file}`.
Поле `code` должно содержать полный текст pytest-файла без markdown fences.
Поле `code` должно содержать только Python-код теста: не добавляй в него закрывающие фигурные скобки JSON, markdown fences, поясняющий текст или второй JSON-объект.
Перед ответом мысленно проверь, что значение поля `code` можно распарсить как Python-файл через `ast.parse`.
Не используй альтернативные имена ключей вроде `file_path`, `source_code`, `path`, `content`, `target_file`.
Не добавляй верхний ключ `target_file`: ниже он обозначает production-файл, который тестируется, а не путь generated test-файла. В ответе путь теста всегда должен быть только в ключе `test_file`.

Режим теста: simple mode.
Нужен небольшой полезный тест нового поведения, а не полное покрытие и не повторение внутреннего алгоритма.

Правила:
- Сгенерируй 1 pytest-файл с 1-3 короткими тестами.
- Тест должен быть самодостаточным: все используемые имена импортированы, определены локально или являются builtin.
- Главный источник поведения — сгенерированный target-код ниже и исходный запрос пользователя.
- Тест обязан вызывать проверяемый target symbol напрямую. Не создавай локальную функцию, метод или wrapper, которые повторяют тело target-кода вместо его вызова.
- Для method-target с fake/self вызывай метод через parent class или bound object на подготовленном self; fake/stub должны быть только окружением target-вызова, а не копией target-логики.
- `planner_json` используй по ролям: explicit_requirements/preserve_literals помогают выбрать наблюдаемое поведение; implementation_constraints помогают setup-у; suggested_reuse не тестируй само по себе; forbidden_assumptions не нарушай. Неподтвержденные детали из planner_json или документации не превращай в обязательные assert-ы.
- Проверяй устойчивые свойства результата: тип, непустое значение, обязательный суффикс/префикс/ключ/литерал, наличие явно заданной даты или id, факт вызова видимого helper-а, изменение видимого состояния.
- Не воспроизводи внутренний алгоритм target-кода, helper-а, dependency method или production contract вручную в assert. Для составных строк, путей, id, структур, сериализованных данных и других вычисляемых результатов получай expected value через тот же видимый production API либо проверяй только устойчивые свойства, прямо следующие из пользовательского запроса: тип, непустоту, принадлежность нужной области, обязательный литерал/суффикс/ключ, факт вызова helper-а или изменение видимого состояния. Не проверяй вручную промежуточные компоненты составного результата и не делай exact equality со всем составным результатом, если точное значение не задано пользователем явно, не является публичным контрактом и не получено через видимый production API.
- Не добавляй отрицательные assert-ы против Unicode, пробелов или исходных фрагментов текста, если пользователь явно этого не требовал и target-код их сохраняет.
- Для project models используй только видимые constructor fields. Не присваивай начальные поля после создания объекта, если их можно передать в конструктор.
- Не придумывай import path, поля, методы, аргументы конструктора и зависимости.
- Для class method импортируй parent class. Если target-код не использует `self`, вызывай метод как `ParentClass.method(None, ...)` и не создавай экземпляр parent class.
- Если parent class указан только как owner/import для вызова метода, это не означает, что нужно создавать его экземпляр.
- Если target-код использует только простые `self`-атрибуты или простые вызовы у них, используй локальный fake/stub/`types.SimpleNamespace`, а не настоящий тяжелый parent instance.
- Если target-derived guidance или `test_plan.avoid` говорят не создавать настоящий parent/project object, используй parent class только для unbound-вызова target-метода на fake self. Общий паттерн: подготовить fake self с нужными атрибутами и вызвать `ParentClass.target_method(fake_self, ...)`. Не вызывай `ParentClass()`.
- Не используй `ParentClass.__new__(ParentClass)` как замену fake self. Это обход конструктора project class, а не простой stub. Подготовь локальный fake self через `types.SimpleNamespace`, `object()` с присвоенными атрибутами или маленький локальный fake class без наследования от parent class.
- Если `test_plan.must_use_symbols` содержит parent class, но parent class нужен только как owner target-метода, это не разрешение создавать реальный экземпляр parent class. Используй этот symbol только для прямого вызова target-метода.
- Не добавляй аргументы тестовой функции для optional pytest plugin fixtures, если такие fixture не видны в related tests/project config. Для UI/GUI code используй monkeypatch/fake/stub без plugin fixture и без запуска event loop.
- Если `test_plan.avoid` запрещает optional pytest plugin fixtures, любая неизвестная fixture в сигнатуре теста является ошибкой генерации теста; перепиши setup через встроенные pytest fixtures или локальные fake/stub объекты.
- Если target-код вызывает методы зависимостей из `self.<dependency>`, а тест проверяет поведение target-а, создай минимальный fake dependency с теми же вызываемыми методами и возвращаемыми видимыми полями. Не создавай настоящий project dependency, не используй файловую систему и не вызывай реальные storage/service/model методы только ради setup, если target можно проверить через fake/stub.
- Если `test_plan.avoid` запрещает symbol/API, не импортируй, не создавай и не используй этот symbol/API в тестовом коде. Для внешнего вызова из target-кода используй monkeypatch на уже импортированном в production-модуле имени или fake module attribute, не импортируя запрещенный внешний API напрямую.
- Не вызывай constructor parent class с `None`, строковой заглушкой, `PurePath` или искусственными аргументами только ради setup, если target-код можно проверить без настоящего instance.
- Для UI/GUI/entrypoint-кода не открывай настоящее окно, не запускай event loop и не вызывай реальный `sys.exit`. Используй monkeypatch/fake/stub или статическую проверку исходного файла.
- Используй `tmp_path` или `monkeypatch` только когда это действительно нужно.
- Не используй pytest-mock/mocker и optional plugin fixtures.
- Негативные тесты добавляй только если они прямо следуют из запроса или target-кода.
- Не добавляй assert на suggested_reuse, если пользователь не требовал этот symbol и target-код не делает его частью наблюдаемого результата.
- Если есть сомнения, выбери самый узкий позитивный тест на реально видимое поведение.
