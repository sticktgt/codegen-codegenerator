Исправь уже сгенерированную правку Python-кода после неудачной автоматической проверки.

Верни только валидный JSON, соответствующий требуемому контракту.

Обязательные ключи верхнего уровня JSON:
- target_file
- target_symbol или target_qualname
- operation
- code
- import_changes
- insert_scope
- expected_new_symbol_kind
- parent_qualname

`import_changes` всегда должен быть JSON-массивом. Если блок `Required repair import_changes` передан ниже, скопируй перечисленные import actions в поле `import_changes` ответа. Недостаточно только исправить `code`.

Приоритет исходного пользовательского запроса.
Выполни требования из блока ниже. Справочный код, документация, комментарии, примеры, related symbols, related tests, reference artifacts, reuse hints и planner wording нужны для понимания проекта, сигнатур, импортов, стиля и допустимых API.
Если справочный контекст противоречит исходному пользовательскому запросу, приоритет имеет исходный пользовательский запрос.

Исходный пользовательский запрос:
{request}

Правила исправления:
- Если исправляешь недоступный широкий сценарий, не заменяй его другим неразрешенным широким методом; используй видимый параметризованный контракт и добавь обязательные параметры в сигнатуру нового symbol.
- Если новый symbol объявлен как возвращающий dict, не возвращай напрямую объект/модель/результат из проектного контракта с недиктовым типом; сформируй dict явно по видимым полям/атрибутам или используй явно видимый проектный helper.
- Если ошибка проверки содержит `unknown_contract_result_attribute`, удали обращение к несуществующему полю результата и сформируй dict только по видимым полям из `contract_result_field_check.visible_return_fields`; если нужных полей нет, верни status="not_repairable".
- Если новый код вызывает метод у внедренной зависимости или поля объекта, этот метод должен быть явно видим в исходном коде целевого символа, контексте модуля/полного файла, связанных символах или контексте контрактов. Не придумывай новые методы зависимостей по смыслу запроса; если нужного метода нет в контексте, используй видимый контракт или измени сигнатуру нового symbol.
- Ограничения видимого project API относятся к project dependencies и внутренним project contracts. Они не запрещают стандартную библиотеку Python и обычные операции явно видимых стандартных типов, если это нужно задаче и не добавляет внешних зависимостей.
- Если ошибка возникла из-за выдуманного project dependency method, не заменяй его другим выдуманным методом: используй видимый контракт, видимый стандартный тип или измени сигнатуру нового symbol.
- Не считай доступ к `__dict__` безопасным способом превратить объект/model в dict. Если contract-функция возвращает объект, model или dataclass-like значение, формируй dict явно по видимым полям, атрибутам, constructor keyword names или явно видимому helper; используй `__dict__` только если project context прямо показывает, что этот тип его поддерживает.
- Сохраняй requested operation из параметров задачи.
- Сохраняй явно указанные пользователем имена методов, функций, классов, параметров и форматы строк результата.
- Приоритет источников поведения: исходный пользовательский запрос важнее repair plan и предыдущего artifact; explicit_requirements и preserve_literals используй как критерии приемки, implementation_constraints как технические ограничения, suggested_reuse как необязательные варианты реализации, а forbidden_assumptions как запреты на неподтвержденные допущения. Старый docstring и старые примеры используй только как документационный контекст.
- Если ошибка проверки содержит `missing_docstring_after_replace`, исправь только документацию target symbol: добавь короткий docstring на русском языке или обнови прежний docstring под новое поведение. Для метода или функции docstring должен быть первой инструкцией внутри тела symbol сразу после строки def/async def. Не меняй исполняемую логику, return-выражения, вызовы helper-ов и import_changes при таком repair.
- Исправленный code обязан сохранить наблюдаемые требования пользовательского запроса, explicit_requirements и preserve_literals. Не удаляй обязательный литерал, формат, префикс/суффикс или return-shape только потому, что старый docstring или previous artifact показывают другой вариант. Не превращай suggested_reuse в обязательный helper-вызов и не нарушай forbidden_assumptions.
- Для замены существующего symbol используй только operation="replace_symbol".
- Для вставки нового symbol после anchor-symbol используй только operation="insert_after_symbol".
- Меняй только target_symbol в указанном target_file или вставляемый новый symbol для anchor.
- Не меняй другие функции и не делай широкий рефакторинг.
- Не пытайся исправлять тестовые файлы или инфраструктурный код.
- Если ошибка проверки указывает на неизвестный self-attribute или invented alias/underscore-поле, замени его на явно видимый атрибут класса из контекста. Не создавай новое поле, если target не является initializer и пользователь явно не просил менять состояние класса.
- Если error context содержит `unknown_self_attribute`, `unknown_self_method` или `unknown_injected_dependency_attribute`, исправленный code не должен содержать указанный неизвестный self-атрибут или self-метод вообще. Используй `suggested_replacements`, `visible_attributes` и `visible_methods`, если они переданы в диагностике.
- Если repair planner перечислил required_changes, итоговый code должен явно реализовать каждое из них. Не повторяй старый вызов или старый receiver, если required_changes требуют поменять аргумент, receiver, import или форму вызова.
- Если critical issue связан с типом аргумента project contract, итоговый вызов должен использовать выражение ожидаемого типа, а не исходную переменную с тем же неподходящим типом.
- Если critical issue связан с неизвестным self-атрибутом или dependency receiver, замени его на точный видимый access path из Allowed API Surface/full-file context либо верни отказ; не создавай новое поле объекта по смыслу запроса.
- Если ошибка проверки показывает, что сгенерированный код использует несуществующий способ найти или получить данные, сначала проверь видимые методы того же класса из контекста. Если среди них есть метод, который покрывает нужную часть поведения и подходит по сигнатуре, используй этот метод вместо выдуманного self-метода или неверного вызова зависимости.
- Если блок "Область repair" указывает "только imports", исправляй только import_changes, import-строки и минимально связанные обращения к импортируемому имени. Не переписывай остальное тело symbol.
- Если имя уже перечислено в блоке "Доступные imports и имена целевого файла", используй это имя без добавления import_changes.
- Если ошибка проверки содержит `unresolved_import_change_module`, убери неподтвержденный внешний import из import_changes и из тела code. Не заменяй его другим неподтвержденным import и не оставляй локальный import внутри try/except. Используй только стандартную библиотеку Python, уже видимые imports/definitions или простую локальную логику.
- Если имя уже доступно в целевом файле через обычный import, guarded import, assignment, class или function definition, используй это имя без повторного import_changes. Если неизвестное имя используется только в необязательной локальной аннотации и запрос не требует сохранить эту аннотацию, предпочитай убрать аннотацию, а не добавлять неподтвержденный внешний import.
- Если ошибка проверки содержит `unknown_runtime_name`, добавь отсутствующий import через import_changes или замени имя на уже видимое имя из целевого файла. Не оставляй в production-коде имена, которых нет в imports, definitions, параметрах или локальных переменных.
- Если одновременно есть `missing_docstring_after_replace` и `unknown_runtime_name`, а исправление unknown name сводится к добавлению подтвержденного import из стандартной библиотеки или видимого контекста, не переписывай исполняемую логику: добавь/обнови docstring и верни нужный import_changes.
- Если неизвестное имя является явно видимым проектным символом из контекста, связанным символом, проектным контрактом, стандартной библиотекой или явно указанной пользователем сущностью с понятным модулем, верни import_changes для этого существующего символа. Такой import не считается новым проектным контрактом. Если путь импорта не подтвержден контекстом, не придумывай его.
- Если передан блок Required repair import_changes, обязательно включи перечисленные элементы в поле import_changes ответа без переименования module/names/action. Недостаточно только переписать поле code: все имена из исправленного code должны быть либо уже доступны в целевом файле, либо добавлены через import_changes.
- Если ошибка проверки указывает на неизвестные keyword-аргументы видимого helper/контракт, исправь вызов по видимой сигнатуре helper/контракт.
- При вызове видимого метода, функции или проектного контракта соблюдай его видимую сигнатуру: порядок, количество и смысл аргументов. Не заменяй объект аргумента заранее вычисленной строкой или другим представлением, если сигнатура ожидает исходный объект или значение другого типа.
- При repair сохраняй границы ответственности видимого helper-а, dependency method или production contract. Не исправляй ошибку путем ручного повторения внутренней сборки результата вокруг helper-вызова и не передавай helper-у заранее частично собранный результат более высокого уровня, если сам helper отвечает за итоговую сборку.
- Если предыдущий artifact смешал ручное форматирование и helper/dependency call для одного результата, упрости решение: оставь один основной источник сборки результата. Либо передай helper-у исходные/подготовленные части по его видимой сигнатуре, либо реализуй результат локально без вызова helper-а, если helper не является обязательным контрактом.
- Если ошибка проверки указывает, что значение используется с операцией, которая не соответствует его видимому типу, не оборачивай это значение механически и не сохраняй ошибочный доступ. Перестрой выражение через видимый атрибут текущего класса, видимый метод вспомогательного объекта или явно видимый проектный контракт.
- Если ошибка проверки указывает, что в конструктор проектной модели передано сериализованное значение вместо видимого типа поля, исправь восстановление данных до создания модели. Не передавай сырые значения из JSON, словаря, файла, записи хранилища или ответа сервиса в поля с непримитивным типом; сначала явно преобразуй их к видимому типу проектным или стандартным способом. Если ошибка указывает, что поле с default получает None при отсутствии сериализованного значения, не передавай это поле в конструктор в такой ветке; собери kwargs и добавляй поле только когда значение действительно восстановлено.
- Если приложен блок "Код, который нужно исправить", исправляй именно его, а не генерируй решение заново.
- Если приложена локальная синтаксическая диагностика, сначала исправь именно эту ошибку минимальным изменением, затем сохрани смысл исходного запроса.
- Если diagnostics сообщает nested symbols, extra symbols, дополнительные sibling symbols или вложенные def/class внутри target symbol, исправленный code должен содержать ровно один `def`/`async def` или `class`: сам заменяемый target symbol. Нельзя просто переименовать вложенный helper: полностью убери вложенное объявление. Полностью убери все дополнительные обработчики, helper-методы, соседние функции и вложенные объявления; не возвращай их повторно и не переименовывай. Не подключай callback к удаленному `self.<handler>`. Встрой нужную минимальную логику в тело target symbol через локальные переменные, lambda, setattr, словари, циклы и выражения либо используй уже видимый проектный контракт.
- Если nested/extra helper был добавлен для поведения, которое не было явно запрошено пользователем и не подтверждено видимым helper/контрактом, не пытайся сохранять это поведение через новый словарь, sibling method, self-helper или переименованный helper. Удали helper и реализуй только минимальную логику, необходимую для исходного запроса и видимого контракта.
- Если приложен блок "Код, который нужно исправить" и в нем уже есть синтаксическая ошибка, не копируй проблемный фрагмент механически: перепиши ошибочную строку или выражение целиком в корректном Python-синтаксисе.
- При переписывании ошибочного выражения убедись, что оно целиком синтаксически завершено: все скобки и кавычки закрыты, а после конца выражения не остается лишних символов.
- Если изменяемое выражение содержит строковый литерал или f-строку, вся итоговая текстовая пунктуация должна находиться внутри этого литерала, а не после него.
- Не повторяй исходный код без изменений, если ниже уже указана ошибка проверки.
- Перед возвратом ответа проверь, что поле code само по себе является валидным Python-кодом для данного symbol.
- Если передан блок Required class members, при replace_symbol класса обязательно сохрани все required=true методы; методы с NotImplementedError нужно реализовать, а не удалять.
- Для requested_operation=replace_symbol верни полный код только целевого symbol. Если target_symbol является методом или функцией, не добавляй второй `def` для обработчика/helper даже когда предыдущий artifact так делал.
- Если передан блок "Сохраняемые элементы текущей реализации", не меняй эти элементы и их порядок при repair, если диагностированная ошибка не относится прямо к ним. Исправляй указанную ошибку минимально и сохраняй форму текущей реализации.
- Если пользовательский запрос требует сохранить существующую структуру или формат, исправляй локально: сохраняй порядок видимых действий, helper-вызовы, аргументы, присваивания, ключи данных и форму return, кроме строк, которые прямо нужно изменить.
- Для requested_operation=replace_symbol не меняй requested insert_scope/parent_qualname/expected_new_symbol_kind: возвращай значения из параметров задачи, если они были переданы.
- Если target_symbol является class, исправленный code должен содержать полное определение этого же класса с тем же именем.
- Нельзя исправлять class-target путем возврата только свободных top-level функций, helper-функций или отдельных методов.
- Если в предыдущей генерации для class-target были возвращены внешние функции вместо класса, исправь результат на полное определение класса.
- Если нужно добавить поведение модели или класса, добавляй его внутрь класса как методы или поля класса, если пользователь явно не попросил свободные функции.
- Нельзя менять requested_operation: repair должен вернуть ту же operation, что указана в параметрах задачи. Если исправление требует другой operation, не пытайся исправлять это через другой тип artifact.
- Для requested_operation=insert_after_symbol не меняй anchor-symbol и верни только код нового symbol.
- Если requested_operation=insert_after_symbol, заполни поле insert_after значением anchor qualname.
- Если requested_operation=insert_after_symbol и insert_scope=class_body, code может начинаться с decorator-строк, относящихся непосредственно к новому method; decorator и следующий def/async def должны быть на одном базовом уровне отступа, а тело метода — на один уровень глубже.
- Если локальная синтаксическая ошибка вызвана unexpected indent в decorated method, минимальное исправление — выровнять decorator и def/async def, не меняя смысл метода и anchor.
- Если целевая правка уже почти корректна, сделай минимальное исправление.
- Минимальное исправление не должно оставлять исходную critical issue нерешенной. После локальной правки перечитай весь code и проверь, что все critical issues из repair request исчезли и не появились новые неизвестные self-атрибуты, receivers, imports или нарушения сигнатур.
- Исправляй только перечисленные critical issues и необходимые следствия этих исправлений. Не добавляй новые UI-вызовы, state changes, helper calls или dependency calls, если они не требуются исходным запросом, diagnostics или repair planner required_changes.
- Если repair planner перечислил `required_changes`, итоговый code должен реализовать их напрямую и не должен добавлять неподтвержденные дополнительные изменения «для надежности».
- Если новый class должен быть dataclass, исправь это напрямую.
- Если запрос просит только модель данных, не добавляй лишнюю логику.
- Reference context используй только как вторичный ориентир по стилю.
- Всегда возвращай import_changes как JSON-массив; если новые imports не нужны, верни [].
- Каждый элемент import_changes должен быть JSON-объектом, а не строкой с Python-import.
  Допустимые формы:
  {{"action": "add_import", "module": "package.module"}}
  {{"action": "add_import", "module": "package.module", "alias": "alias_name"}}
  {{"action": "add_from_import", "module": "package.module", "names": ["Name"]}}
  {{"action": "remove_import", "module": "package.module"}}
  {{"action": "remove_from_import", "module": "package.module", "names": ["Name"]}}
- Не возвращай import_changes вида ["from package.module import Name"] или ["import package.module"]; это строка, а не structured artifact contract.
- Не добавляй import-строки внутрь поля code: все новые imports описывай через import_changes.
- Не оставляй локальные imports в repaired code, даже если они уже были в previous artifact. Если имя нужно итоговому code, перенеси его в `import_changes`; если не нужно — убери.
- Итоговый repaired code должен быть самодостаточным относительно imports: каждое external/module-level имя должно быть уже доступно в целевом файле или добавлено через import_changes ответа.
- При repair не теряй корректный import из previous artifact, если соответствующее имя осталось в итоговом repaired code и не доступно иначе.
- Форма import_changes должна соответствовать форме использования имени в code; не добавляй неиспользуемые imports. Если одно и то же имя есть и в import_changes, и локально внутри function/method body, правильная чистка — сохранить/добавить module-level import_changes и убрать локальный import из code, а не удалять import_changes для имени, которое остается использованным.
- Не вводи новые import aliases без явной причины из исходного файла, пользовательского запроса или подтвержденного контекста.
- Используй remove_import/remove_from_import только для imports, видимых в исходном файле и реально не нужных итоговому code. Advisory diagnostics про duplicated/local import не является причиной удалять module-level import_changes, если имя остается использованным.
- Если создаешь проектную модель, DTO, dataclass-like объект или result-object, используй только явно видимые constructor fields / keyword names из model surfaces, source excerpt или сигнатуры `__init__`. Не заменяй их близкими по смыслу alias-именами и не переименовывай аргументы из пользовательского запроса.
- Если исходный запрос или предыдущий artifact явно требует вернуть или создать конкретный result/model object, repair не должен заменять этот объект на словарь. Исправляй import_changes и constructor keywords так, чтобы остался требуемый result/model object.
