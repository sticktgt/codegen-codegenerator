Исправь уже сгенерированную правку Python-кода после неудачной автоматической проверки.

Верни только валидный JSON, соответствующий требуемому контракту.

Обязательные ключи верхнего уровня JSON:
- target_file
- target_symbol или target_qualname
- operation
- code
- import_changes
- insert_scope
- expected_new_symbol_kind
- parent_qualname

`import_changes` всегда должен быть JSON-массивом. Если блок `Required repair import_changes` передан ниже, скопируй перечисленные import actions в поле `import_changes` ответа. Недостаточно только исправить `code`.

Правила исправления:
- Если исправляешь недоступный широкий сценарий, не заменяй его другим неразрешенным широким методом; используй видимый параметризованный контракт и добавь обязательные параметры в сигнатуру нового symbol.
- Если новый symbol объявлен как возвращающий dict, не возвращай напрямую объект/модель/результат из проектного контракта с недиктовым типом; сформируй dict явно по видимым полям/атрибутам или используй явно видимый проектный helper.
- Если ошибка проверки содержит `unknown_contract_result_attribute`, удали обращение к несуществующему полю результата и сформируй dict только по видимым полям из `contract_result_field_check.visible_return_fields`; если нужных полей нет, верни status="not_repairable".
Если новый код вызывает метод у внедренной зависимости или поля объекта, например `self.<dependency>.<method>(...)`, этот метод должен быть явно видим в исходном коде целевого символа, контексте модуля/полного файла, связанных символах или контексте контрактов. Не придумывай новые методы зависимостей по смыслу запроса; если нужного метода нет в контексте, используй видимый контракт или измени сигнатуру нового symbol.
- Блок Allowed API Surface ограничивает вызовы методов и атрибутов проектных зависимостей, сервисов, вспомогательных объектов проекта и внутренних проектных контрактов. Он не запрещает использовать стандартную библиотеку Python и обычные методы явно видимых стандартных типов, если это нужно для задачи, не добавляет внешних зависимостей и не противоречит видимому коду.
- Если ошибка возникла из-за выдуманного метода проектной зависимости, не заменяй его другим выдуманным методом. Сначала проверь, можно ли выполнить задачу обычными средствами стандартной библиотеки или методами явно видимого стандартного типа, либо через уже видимый проектный контракт.
- Не считай отсутствие метода стандартного типа в Allowed API Surface причиной отказаться от реализации. Это ограничение применяется к проектным зависимостям и внутренним проектным контрактам, а не к стандартной библиотеке Python.
- Не считай доступ к `__dict__` безопасным способом превратить объект/model в dict. Если contract-функция возвращает объект, model или dataclass-like значение, формируй dict явно по видимым полям, атрибутам, constructor keyword names или явно видимому helper; используй `__dict__` только если project context прямо показывает, что этот тип его поддерживает.
- Сохраняй requested operation из параметров задачи.
- Сохраняй явно указанные пользователем имена методов, функций, классов, параметров и форматы строк результата.
- Если старый docstring, предыдущий artifact или repair plan противоречат исходному запросу пользователя, используй исходный запрос пользователя как источник истины. Не восстанавливай устаревшее поведение из старого описания.
- Если в запросе есть блок Явные требования запроса к результату и литералам, исправленный code обязан сохранить эти наблюдаемые требования. Не удаляй обязательный литерал, формат, префикс/суффикс или return-shape только потому, что старый docstring или previous artifact показывают другой вариант.
- Для замены существующего symbol используй только operation="replace_symbol".
- Для вставки нового symbol после anchor-symbol используй только operation="insert_after_symbol".
- Меняй только target_symbol в указанном target_file или вставляемый новый symbol для anchor.
- Не меняй другие функции и не делай широкий рефакторинг.
- Не пытайся исправлять тестовые файлы или инфраструктурный код.
- Если ошибка проверки указывает на неизвестный self-attribute или invented alias/underscore-поле, замени его на явно видимый атрибут класса из контекста. Не создавай новое поле, если target не является initializer и пользователь явно не просил менять состояние класса.
- Если error context содержит `unknown_self_attribute`, `unknown_self_method` или `unknown_injected_dependency_attribute`, исправленный code не должен содержать указанный неизвестный self-атрибут или self-метод вообще. Используй `suggested_replacements`, `visible_attributes` и `visible_methods`, если они переданы в диагностике.
- Если ошибка проверки показывает, что сгенерированный код использует несуществующий способ найти или получить данные, сначала проверь видимые методы того же класса из контекста. Если среди них есть метод, который покрывает нужную часть поведения и подходит по сигнатуре, используй этот метод вместо выдуманного self-метода или неверного вызова зависимости.
- Если блок "Область repair" указывает "только imports", исправляй только import_changes, import-строки и минимально связанные обращения к импортируемому имени. Не переписывай остальное тело symbol.
- Если имя уже перечислено в блоке "Доступные imports и имена целевого файла", используй это имя без добавления import_changes.
- Если ошибка проверки содержит `unknown_runtime_name`, добавь отсутствующий import через import_changes или замени имя на уже видимое имя из целевого файла. Не оставляй в production-коде имена, которых нет в imports, definitions, параметрах или локальных переменных.
- Если неизвестное имя является явно видимым проектным символом из контекста, связанным символом, проектным контрактом, стандартной библиотекой или явно указанной пользователем сущностью с понятным модулем, верни import_changes для этого существующего символа. Такой import не считается новым проектным контрактом. Если путь импорта не подтвержден контекстом, не придумывай его.
- Если передан блок Required repair import_changes, обязательно включи перечисленные элементы в поле import_changes ответа без переименования module/names/action. Недостаточно только переписать поле code: все имена из исправленного code должны быть либо уже доступны в целевом файле, либо добавлены через import_changes.
- Если ошибка проверки указывает на неизвестные keyword-аргументы видимого helper/контракт, исправь вызов по видимой сигнатуре helper/контракт.
- Если ошибка проверки указывает, что значение используется с операцией, которая не соответствует его видимому типу, не оборачивай это значение механически и не сохраняй ошибочный доступ. Перестрой выражение через видимый атрибут текущего класса, видимый метод вспомогательного объекта или явно видимый проектный контракт.
- Если ошибка проверки указывает, что в конструктор проектной модели передано сериализованное значение вместо видимого типа поля, исправь восстановление данных до создания модели. Не передавай сырые значения из JSON, словаря, файла, записи хранилища или ответа сервиса в поля с непримитивным типом; сначала явно преобразуй их к видимому типу проектным или стандартным способом. Если ошибка указывает, что поле с default получает None при отсутствии сериализованного значения, не передавай это поле в конструктор в такой ветке; собери kwargs и добавляй поле только когда значение действительно восстановлено.
- Если приложен блок "Код, который нужно исправить", исправляй именно его, а не генерируй решение заново.
- Если приложена локальная синтаксическая диагностика, сначала исправь именно эту ошибку минимальным изменением, затем сохрани смысл исходного запроса.
- Если diagnostics сообщает nested symbols или вложенные def/class внутри target symbol, исправленный code не должен содержать никаких дополнительных `def` или `class`, кроме самого заменяемого target symbol. Нельзя просто переименовать вложенный helper; полностью убери вложенное объявление и встрои логику в тело target symbol через локальные переменные, словари, циклы и выражения либо используй уже видимый проектный контракт.
- Если приложен блок "Код, который нужно исправить" и в нем уже есть синтаксическая ошибка, не копируй проблемный фрагмент механически: перепиши ошибочную строку или выражение целиком в корректном Python-синтаксисе.
- При переписывании ошибочного выражения убедись, что оно целиком синтаксически завершено: все скобки и кавычки закрыты, а после конца выражения не остается лишних символов.
- Если изменяемое выражение содержит строковый литерал или f-строку, вся итоговая текстовая пунктуация должна находиться внутри этого литерала, а не после него.
- Не повторяй исходный код без изменений, если ниже уже указана ошибка проверки.
- Перед возвратом ответа проверь, что поле code само по себе является валидным Python-кодом для данного symbol.
- Если передан блок Required class members, при replace_symbol класса обязательно сохрани все required=true методы; методы с NotImplementedError нужно реализовать, а не удалять.
- Для requested_operation=replace_symbol верни полный код только целевого symbol.
- Если передан блок "Сохраняемые элементы текущей реализации", не меняй эти элементы и их порядок при repair, если диагностированная ошибка не относится прямо к ним. Исправляй указанную ошибку минимально и сохраняй форму текущей реализации.
- Если пользовательский запрос требует сохранить существующую структуру или формат, исправляй локально: сохраняй порядок видимых действий, helper-вызовы, аргументы, присваивания, ключи данных и форму return, кроме строк, которые прямо нужно изменить.
- Для requested_operation=replace_symbol не меняй requested insert_scope/parent_qualname/expected_new_symbol_kind: возвращай значения из параметров задачи, если они были переданы.
- Если target_symbol является class, исправленный code должен содержать полное определение этого же класса с тем же именем.
- Нельзя исправлять class-target путем возврата только свободных top-level функций, helper-функций или отдельных методов.
- Если в предыдущей генерации для class-target были возвращены внешние функции вместо класса, исправь результат на полное определение класса.
- Если нужно добавить поведение модели или класса, добавляй его внутрь класса как методы или поля класса, если пользователь явно не попросил свободные функции.
- Для requested_operation=insert_after_symbol не меняй anchor-symbol и верни только код нового symbol.
- Если requested_operation=insert_after_symbol, заполни поле insert_after значением anchor qualname.
- Если requested_operation=insert_after_symbol и insert_scope=class_body, code может начинаться с decorator-строк перед методом, например @property; decorator и следующий def/async def должны быть на одном базовом уровне отступа, а тело метода — на один уровень глубже.
- Для @property не меняй technical kind на property: возвращай expected_new_symbol_kind из параметров задачи, обычно "method".
- Если локальная синтаксическая ошибка вызвана unexpected indent в decorated method, минимальное исправление — выровнять decorator и def/async def, не меняя смысл метода и anchor.
- Если целевая правка уже почти корректна, сделай минимальное исправление.
- Если новый class должен быть dataclass, исправь это напрямую.
- Если запрос просит только модель данных, не добавляй лишнюю логику.
- Reference context используй только как вторичный ориентир по стилю.
- Всегда возвращай import_changes как JSON-массив; если новые imports не нужны, верни [].
- Import через import_changes допустим для уже существующих символов проекта, которые явно видны в контексте или в исходном запросе с подтвержденным модулем, а также для стандартной библиотеки Python. Не добавляй import path, который нельзя подтвердить контекстом.

- Для project symbol используй только точный module path, явно видимый в контексте рядом с этим symbol: qualname, module_name, file_path, import context или source excerpt. Не преобразуй путь по аналогии, не заменяй его на общие модули вроде `models`, `utils`, `schemas`, `helpers` без прямого подтверждения в контексте.
- Если несколько нужных project symbols видны в одном и том же module_name, можно импортировать их из этого module_name одним `add_from_import`. Имена в `names` должны совпадать с фактически видимыми именами symbols.
- Если создаешь проектную модель, DTO, dataclass-like объект или result-object, используй только явно видимые constructor fields / keyword names из model surfaces, source excerpt или сигнатуры `__init__`. Не заменяй их близкими по смыслу alias-именами и не переименовывай аргументы из пользовательского запроса.
- Если исходный запрос или предыдущий artifact явно требует вернуть или создать конкретный result/model object, repair не должен заменять этот объект на словарь. Исправляй import_changes и constructor keywords так, чтобы остался требуемый result/model object.
- Не добавляй import-строки внутрь поля code.
- Если import_changes добавил import, который не используется в исправленном code, удали этот import из import_changes или измени code так, чтобы использовалось именно импортированное имя.
- Не дублируй один и тот же import на уровне файла через import_changes и внутри функции.
- Если используешь квалифицированное имя модуля, например `module.function(...)`, верни `add_import` для модуля; если используешь имя функции напрямую, верни `add_from_import` для этой функции.
- Если исправленный code использует имя, которого нет среди существующих imports или definitions целевого файла, верни нужный import в import_changes. Это относится к именам в теле функции, type annotations, default values, decorators, context managers и helper calls.
- Не полагайся на from __future__ import annotations как причину пропустить import для явно использованного annotation type. Если используешь внешний тип в сигнатуре, добавь import_changes.
- Если ошибка проверки указывает на нарушение сигнатуры связанного проектного контракта, исправь именно вызов: передай обязательные аргументы согласно сигнатуре или выбери решение, которое не вызывает этот symbol некорректно.
- Если диагностика формулирует это как нарушение сигнатуры связанного production-контракта, трактуй его так же: исправь вызов по видимой сигнатуре, а не меняй сценарий по догадке.
- Если в контексте есть Required production contract calls, исправленный code обязан вызвать эти production-контракты; не заменяй их ручной реализацией бизнес-логики.

- Если передан блок Contract attribute requirements, используй его только как дополнительный структурный контекст о полях моделей и контрактов; не добавляй новые поля и не подменяй явно видимые поля alias-именами.
- Если обязательный аргумент contract symbol нельзя получить из параметров нового symbol, локальных переменных, target context или явно видимого проектного контекста, не подставляй придуманный литерал-заглушку вроде общей строки или условного значения; вместо этого измени сигнатуру нового symbol так, чтобы нужный аргумент был передан вызывающим кодом, или выбери другой видимый контракт.
Если contract context показывает существующий caller для того же production symbol, сначала адаптируй видимый calling pattern этого caller: перенеси необходимые параметры в новый symbol и передавай их в production call. Не заменяй такие параметры фиктивными константами, общими строками, None или агрегирующими значениями, если они не указаны пользователем явно.
- Если ошибка проверки указывает на дубликат symbol или повтор существующего метода/функции, не возвращай этот же symbol повторно: создай новый symbol с уникальным именем, соответствующим исходному пользовательскому запросу.
- Пример add_from_import: {{"action": "add_from_import", "module": "pathlib", "names": ["Path"]}}.
- Пример add_import: {{"action": "add_import", "module": "json"}}.

Перед возвратом JSON проверь: если в code есть SearchResult/build_context_fragment/find_match_positions или другие имена из Required repair import_changes, поле import_changes должно содержать соответствующий add_from_import.
