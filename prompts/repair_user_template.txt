Исправь уже сгенерированную правку Python-кода после неудачной автоматической проверки.

Верни только валидный JSON, соответствующий требуемому контракту.

Правила исправления:
- Сохраняй requested operation из параметров задачи.
- Сохраняй явно указанные пользователем имена методов, функций, классов, параметров и форматы строк результата.
- Для замены существующего symbol используй только operation="replace_symbol".
- Для вставки нового symbol после anchor-symbol используй только operation="insert_after_symbol".
- Меняй только target_symbol в указанном target_file или вставляемый новый symbol для anchor.
- Не меняй другие функции и не делай широкий рефакторинг.
- Не пытайся исправлять тестовые файлы или инфраструктурный код.
- Если приложен блок "Код, который нужно исправить", исправляй именно его, а не генерируй решение заново.
- Если приложена локальная синтаксическая диагностика, сначала исправь именно эту ошибку минимальным изменением, затем сохрани смысл исходного запроса.
- Если приложен блок "Код, который нужно исправить" и в нем уже есть синтаксическая ошибка, не копируй проблемный фрагмент механически: перепиши ошибочную строку или выражение целиком в корректном Python-синтаксисе.
- При переписывании ошибочного выражения убедись, что оно целиком синтаксически завершено: все скобки и кавычки закрыты, а после конца выражения не остается лишних символов.
- Если изменяемое выражение содержит строковый литерал или f-строку, вся итоговая текстовая пунктуация должна находиться внутри этого литерала, а не после него.
- Не повторяй исходный код без изменений, если ниже уже указана ошибка проверки.
- Перед возвратом ответа проверь, что поле code само по себе является валидным Python-кодом для данного symbol.
- Для requested_operation=replace_symbol верни полный код только целевого symbol.
- Для requested_operation=insert_after_symbol не меняй anchor-symbol и верни только код нового symbol.
- Если requested_operation=insert_after_symbol, заполни поле insert_after значением anchor qualname.
- Если целевая правка уже почти корректна, сделай минимальное исправление.
- Если новый class должен быть dataclass, исправь это напрямую.
- Если запрос просит только модель данных, не добавляй лишнюю логику.
- Reference context используй только как вторичный ориентир по стилю.
- Всегда возвращай import_changes как JSON-массив; если новые imports не нужны, верни [].
- Не добавляй import-строки внутрь поля code.
- Если исправленный code использует имя, которого нет среди существующих imports или definitions целевого файла, верни нужный import в import_changes. Это относится к именам в теле функции, type annotations, default values, decorators, context managers и helper calls.
- Не полагайся на from __future__ import annotations как причину пропустить import для явно использованного annotation type. Если используешь внешний тип в сигнатуре, добавь import_changes.
- Пример add_from_import: {{"action": "add_from_import", "module": "pathlib", "names": ["Path"]}}.
- Пример add_import: {{"action": "add_import", "module": "json"}}.
