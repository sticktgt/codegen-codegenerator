Подготовь краткий план генерации pytest-теста.

Верни только валидный JSON.

Обязательные поля JSON:
- target_symbol
- test_intent
- must_use_symbols
- avoid

Правила:
- Планируй тест только по видимому проектному контексту. Если передан сгенерированный target-код, именно он является главным источником истины для теста. Справочный контекст целевого файла до изменения используй только для импортов, стиля, окружающего кода и старых публичных контрактов.
- Не придумывай import path, поля, методы, аргументы конструктора и атрибуты.
- must_use_symbols должен включать тестируемый symbol и только те project symbols, которые реально нужны для теста.
- Планируй test-функции без fixture-параметров, если fixture-параметры явно не показаны в связанных тестах проекта.
- Не планируй optional pytest plugin fixtures и plugin-specific patch/mock.
- Если нужен контроль зависимости или результата, предпочитай локальные fake/stub классы.
- Если patch действительно необходим, планируй только стандартную библиотеку Python.
- Блок Allowed API Surface ограничивает проектные зависимости и внутренние проектные контракты. Он не запрещает использовать стандартную библиотеку Python и обычные методы явно видимых стандартных типов в тесте, если это не добавляет внешних зависимостей и соответствует видимому коду.
- Если для подготовки тестовых данных нужен временный файл, директория, коллекция, строка, дата, путь или другой простой объект стандартной библиотеки, используй обычные средства стандартной библиотеки и явно видимые стандартные типы. Не придумывай для этого новые проектные helper-методы или новые аргументы конструктора.
- Если operation=insert_after_symbol, target_symbol уже указывает на новый symbol для тестирования, а не на anchor-symbol.
- Если insert_scope=class_body, target_symbol указывает на метод класса: тест должен использовать parent class, создать экземпляр по видимой сигнатуре конструктора и вызывать метод через этот экземпляр.
- Если для создания экземпляра parent/project class в видимом __init__ есть обязательные параметры без default-значений, планируй передачу валидных тестовых значений для всех таких параметров. Не планируй вызов конструктора без обязательных аргументов.
- Планируй создание project class только с видимыми constructor_fields/аргументами конструктора. Не планируй дополнительные keyword-аргументы для helper/dependency, если их нет в видимой сигнатуре конструктора.
- Для dict результата ожидаемые значения должны следовать из target source и явно видимых defaults/полей моделей; не придумывай expected values.
- Если тест проверяет модель или доменный объект, восстановленный из JSON, словаря, файла, записи хранилища или другого сериализованного источника, ожидаемые значения должны соответствовать видимым типам полей модели, а не сырому сериализованному представлению. Если сериализованное поле отсутствует, а у модели есть значение по умолчанию, планируй проверку default-поведения модели, а не проверку None.
- Если expected value зависит от default field values модели, вычисляй его из этих defaults и данных теста.
- Если передан блок Contract attribute requirements, test data/fake/stub обязаны реализовать перечисленные required_fields; для реальных project models используй только constructor_fields, а не похожие alias-поля.
- Все текстовые значения JSON пиши на русском языке.
