Подготовь краткий план генерации pytest-теста.

Верни только валидный JSON.

Обязательные поля JSON:
- target_symbol
- test_intent
- must_use_symbols
- avoid

Правила:

1. Источники истины
- Планируй тест только по видимому проектному контексту.
- Если передан сгенерированный target-код, именно он является главным источником проверяемого поведения.
- Если в запросе есть блок Explicit request output and literal obligations, ожидаемые значения теста должны сохранять эти требования. Не бери ожидаемый формат из старого docstring или старого source, если он противоречит явному CR.
- Справочный исходный файл до изменения используй для импортов, стиля, конструктора parent class и старых публичных контрактов, но не для переопределения поведения target-кода.
- Related tests используй только если они переданы и не противоречат target-коду, model surfaces, source excerpt или видимым сигнатурам.

2. Импорты и project symbols
- Для project symbols в must_use_symbols указывай только symbols с явно видимым module path/qualname.
- Если передан блок Required project imports, must_use_symbols и import paths должны соответствовать этому блоку; не заменяй их похожими модулями по названию.
- Тестовый файл должен быть самодостаточным: каждое используемое имя должно быть импортировано, определено локально, передано как параметр тестовой функции или быть builtin-именем. Если планируешь использовать symbol из стандартной библиотеки или проекта, планируй явный import в начале теста.
- Не придумывай import path, поля, методы, аргументы конструктора и атрибуты.
- Не импортируй методы класса как top-level functions. Для class_body method импортируй parent class и вызывай метод через экземпляр.

- Если тесту нужен вызов project contract из contract context, не планируй вызов с меньшим числом обязательных аргументов, чем указано в видимой сигнатуре этого контракта.

3. Создание проектных объектов
- Создавай project class/model только через видимый конструктор или через явно показанный в проектном контексте способ создания.
- Передавай все обязательные аргументы конструктора и только те keyword-аргументы, которые видны в сигнатуре, model surfaces, source excerpt или related/context source.
- Значения аргументов должны быть совместимы с видимыми типами. Не заменяй типизированные аргументы строками, None или произвольными заглушками, если в контексте виден более точный тип.
- Если сигнатура конструктора неясна, используй явно показанный project-context пример; если такого примера нет, планируй fake/stub вместо создания непонятного project object.
- Если передан recommended setup для parent instance, планируй создание объекта по этому шаблону; не заменяй его строковыми заглушками, `None`, `__new__` или произвольным минимальным конструктором.
- Метаданные CR вроде `Title:` не являются полями модели и не дают права использовать constructor keyword `title`, если он не виден в model surfaces.
- Не планируй создание project class через `__new__`, если виден обычный конструктор `__init__`.

4. Управление зависимостями и helper-вызовами
- Если target-код вызывает helper того же экземпляра через `self.<helper>(...)`, тест должен контролировать этот видимый helper через instance-level fake/lambda с той же сигнатурой вызова.
- Если target-код получает данные через видимый helper/dependency, а тест подменяет этот источник через fake/stub/lambda/monkeypatch, эта подмена является достаточной подготовкой данных. Не планируй дополнительные вызовы persistence/storage/repository/save/load/create/update методов и не создавай скрытое состояние объекта (`_items`, `_notes`, `_storage`, `_records`), если target-код сам не вызывает эти методы и они не нужны для проверяемого поведения.
- Не подменяй свободную helper-функцию в исходном модуле helper-а, если target-код использует direct import этой функции. Используй реальный helper и вычисляй expected values через него, либо patch binding в модуле target-кода.
- Не планируй вызовы методов project object, которых нет в видимом class source, full file source или source excerpt.
- Если нужен контроль зависимости или результата, предпочитай локальные fake/stub классы или стандартный pytest monkeypatch; optional pytest plugin fixtures и plugin-specific patch/mock запрещены.
- По умолчанию планируй test-функции без fixture-параметров. Встроенные pytest fixtures `tmp_path` и `monkeypatch` допустимы, когда они прямо нужны для файлового ресурса, Path-аргумента или безопасной подмены binding.

5. Ожидания и проверки
- Ожидаемые значения должны следовать из target-кода, явно заданных данных теста, видимых default-значений модели и видимых helper-функций.
- Если ожидаемый результат зависит от значений по умолчанию в модели, используй видимые default-значения модели, а не придумывай собственные.
- Если тест проверяет модель или доменный объект, восстановленный из JSON, словаря, файла или записи хранилища, ожидаемые значения должны соответствовать видимым типам полей модели, а не сырому сериализованному представлению.
- Если передан блок Contract attribute requirements, test data/fake/stub обязаны реализовать перечисленные required_fields; для реальных project models используй constructor_fields, а не похожие alias-поля.
- Если operation=insert_after_symbol, target_symbol уже указывает на новый symbol для тестирования, а не на anchor-symbol.
- Если insert_scope=class_body, target_symbol указывает на метод класса: тест должен использовать parent class, создать экземпляр по видимой сигнатуре конструктора и вызывать метод через этот экземпляр.
- Все текстовые значения JSON пиши на русском языке.
